# 核心概念

五个想法支撑整个引擎。你会遇到的每个 API 都是它们戴着某顶帽子的样子。

## 1. 唯一权威会话

Story 解析为确定性模拟；会话拥有状态。一切写入都经过**命令**——要么提交完整有效的结果，要么不留任何痕迹。命令日志、存档、重放、玩家回滚全都挂在这一条脊柱上。

```text
Story 定义 -> 解析后的 GameSimulation -> GameSession/GameSnapshot
 -> GameQueries -> 语义发布 -> 表现层 -> 渲染器
```

UI 与自动化从不直接改状态——它们派发**语义 invocation**（"陪猫玩"、"开门营业"），由适配器映射为命令。

## 2. 模块拥有状态槽

玩法状态拆分为模块（日历、猫、店铺……），每个模块拥有一个带 schema 和版本号的受校验槽位。一条命令跨模块的效果在一个原子事务里提交。随机数来自事务性 RNG，其状态存在快照里——回滚后重试会得到完全相同的结果。

## 3. 静态数据是内容，不是状态

物品表、活动定义、事件候选、反应规则是**内容数据库表**：定义期全量校验（主键、跨表引用、文本引用），通过类型化只读查询面使用（`byId`、带条件的 `findMany`），运行时永不修改。边界是硬的——游玩中会变的属于模块；创作时定义的属于表。

## 4. 舞台是语义的

屏幕上的东西用纯数据描述：图层、带内容 ID 的条目、整数位置、外观、可选的命中区域。内容目录把 ID 解析为渲染器 props；React 渲染器负责绘制；viewport 把整个逻辑画布等比缩放（设计分辨率上的绝对布局——静态美术作为整体缩放）。指针、触摸、键盘落在同一条语义路径上。

## 5. 解释是数据

事件池的抽取报告候选、权重与 roll。被拒的命令返回结构化代码。诊断是类型化信封。瞬态演出反馈从已提交的 fact 派生。这就是引擎对 AI 代理可读、对人类可调试的原因——同一批解释对象同时喂给测试、DevDock 面板和模拟报告。
