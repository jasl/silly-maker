# template/ agent handbook

This package is the **scene-first starter for a new game** (MIT). Its ordinary `/` entry is deliberately minimal: it does not import DevDock, preset settings, Inspector, Agent, or the private Extension/Mod Runtime. `/reference.html` is the separate runnable first-party outer-UI example. Start this application's dev server with `deno task dev` from the copied project or `deno task app dev template` from the repository root, then open the same-origin `/__sillymaker/inspector/` page (the reference DevDock also advertises it). The dev-only Inspector enumerates Authoring Scene documents, renders the real Stage plus a Layer/Object hierarchy, edits local transform/content/appearance/order, joins read-only facets, and saves through the Scene CAS port. The opening authority is `src/scenes/opening/opening.authoring-scene.json`; cue and Motion declarations that the bounded Inspector does not edit remain ordinary source-data edits. The TypeScript layers below stay the advanced path.

To start a new story: copy this directory to `examples/<new-name>` (or anywhere outside the repository) → global rename (`template`/`Template` → the new name) → update `sillymaker.config.ts` (applicationId/label) and `metadata.json` (page title / share card) → replace the script and modules as needed. Inside this repository, also add the directory to the root `project.config.ts` list; outside it, point the `package.json` dependencies at the engine packages by relative `file:` path and set `"nodeModulesDir": "manual"` in the project's `deno.json`. Format with `deno fmt` (the workspace `deno task format`); do not add Prettier. The copy is a complete project: `deno task dev`, `deno task build:web` / `build:desktop` / `deploy:cf` / `preview` / `clean`, and `deno task app check .` run from the directory itself (`deploy:cf` publishes `dist-web/` as a standalone Cloudflare Worker — rename `name` in `wrangler.jsonc` with the rest of the project).

Change discipline: keep it minimally playable. The placeholder script may be replaced wholesale; do not grow new gameplay structure on the skeleton (that belongs in examples or real games). `application/**` is the Advanced layer — ordinary scene authoring does not edit these files.

## Browser pitfalls: engine-covered vs. game-side

Already covered by the engine (do not re-handle in a Story): text selection / image dragging / iOS long-press callout / double-tap zoom delay / scroll chaining and pull-to-refresh (stage CSS), right-click semantics (controls have no default action, scene background = close the topmost surface, controls may opt in via `data-secondary-action`), audio autoplay unlock and pause-on-hidden, reduced-motion degradation, stacking scales, window chrome and focus.

The game side must handle these itself (the engine cannot):

- **Keep the simulation layer DOM-clean**: `game/simulation.ts`/`game/state.ts`/content tables must not reference `window`/`document`/`matchMedia` (headless runs and replay break); browser APIs appear only under `application/` (`composition.tsx` / `ui.tsx`).
- **Application-layer file roles**: `composition.tsx` = projector, slots, labels, the `*GameApplicationV1` declaration, its `application.ui().narrative` definition, and selection of the focused default VN Player; product-owned PascalCase HUD/panel or special-surface components live in `ui.tsx`; `core-application.ts` = the headless instance factory; `entry.tsx` boots from `composition.tsx`.
- **No `Math.random()` or `Date.now()` on deterministic paths**: randomness goes through the transaction RNG, time through the engine clock.
- **Bilingual text overflow**: eyeball long strings in both languages (English often runs 30%+ longer than Chinese); lay out HUD/buttons flexibly.
- **Touch targets ≥ 32px**: compact buttons are already at the floor; do not shrink further.
- **Use engine hooks instead of hand-rolling**: asset URLs via `useAssetUrlV1`/`resolveAssetUrlV1`, motion gating via `useReducedMotionV1`, gameplay windows via `defineWorkspaceOverlayV1` + `slots.overlayResolver` + the normal presentation-intent path (with `context.overlays` only for structural detail/back/close) — the Host supplies `PanelV1`; hand-rolled copies miss the pitfalls the engine already fixed.
- **Browser-test settle signals**: wait on `[data-semantic-stage][data-stage-settled="true"]` for stage transitions (a crossfade keeps old and new entries mounted until it flips) and publish `playerView.revealComplete` as a Story-owned `data-dialogue-*` attribute (this template: `data-dialogue-reveal="complete"`) so e2e waits on one selector instead of looping clicks or counting images.

## Engine baseline (free; do not rewrite)

Declaring `titleScreen` (title / background art / optional `splash` intro lines) yields the full front door: splash → title screen (New game / Continue / Load game / Settings). Splash and Title are package-owned WholeCanvas renderers, but their authoring shape remains this existing `titleScreen` declaration; do not duplicate them in `application.ui().wholeCanvas`. The system menu is single-modal (save and settings are mutually exclusive; Esc / right-click / backdrop click closes the topmost surface; a window may declare `dismissible: false` to lock, in which case only its explicit close control works). The save dialog ships with slot lists, timestamps, import/export, and load-enters-gameplay. The core settings host renders product-supplied sections; the first-party volume/mute, text speed, auto-wait, fullscreen, optional skip-cutscene, and developer-tools controls come from the explicit reference outer UI. A Story may use `playerProfile.current().preferences.skipCutscenes` to settle skippable presentation waits; it must never bypass authoritative scheduler time or semantic commands.

## Optional wiring (one entry point each)

- **Reference outer UI**: opt in with `outerUi: createReferencePlayerOuterUiV1(...)` from `@sillymaker/web/reference`. It composes `@sillymaker/ui/reference` preset settings plus DevDock and accepts a lazy `loadContributions` boundary. Keep the default Template entry minimal; copy/eject or replace this composition when the product needs custom tooling/settings chrome.
- **Web metadata**: `metadata.json` (title/description/share card/favicon), injected into `<head>` at build time.
- **Audio**: declare audio assets with `resolveAudioManifestV1` (digest required) → project `AudioIntentV1` from the view (bgm/ambient/voice, restored on load) → mount `GameAudioV1` in the UI (map one-shot SFX from transient effects via `resolveEffectAsset`).
- **Narrative surface**: declare the Story's one production writer as `narrative: defineNarrativeSurfaceV1(...)` inside `application.ui()`. The starter selects `createDefaultVnPlayerV1` from `@sillymaker/ui/narrative-player`, which supplies the usable renderer plus Enter/Space/Tab/H/Ctrl and PageUp/PageDown/wheel Back/Forward defaults; applications provide semantic selection/dispatch, text IDs, `instance.rollback`, and optional current-voice replay. Products that do not need History UI may instead select `createDefaultVnPlayerCoreV1` from `@sillymaker/ui/narrative-player/core` and omit the Narrative definition's `history` feature; this removes the History presentation graph without changing Story-owned History State or Save authority. Theme the preset through its `--silly-vn-player-*` variables. A genuinely different VN surface may copy/eject or replace the renderer, but must not mount both or mirror composition-owned playback/History/focus state.
- **WholeCanvas surface**: declare the Story's one optional definition as `wholeCanvas: defineWholeCanvasSurfaceV1(...)` inside `application.ui()`. Use a publication selector when semantic state owns the primary, or the narrow `createWholeCanvasApplicationSourceV1` for presentation-only replacement/detail navigation (Engine Lab's exact-query rig). Supply the catalog, target resolver, owner-action dispatcher, passive renderer, optional preparation, and text resolver; the renderer consumes immutable primary/detail frames and calls only frame-bound `onAction` / `onBack`. The package owns readiness, exact-parent detail, input, focus, Stage placement, and Splash/Title. Do not add a Root slot, local visibility boolean, or second Host; omit `wholeCanvas` entirely when unused.
- **Player rollback**: add `rollback: { capacity, classify }` to the core definition. Use `checkpoint` for player-visible interaction boundaries, `transparent` for internal settlement such as hold ticks, and `barrier` for irreversible commands. The UI uses the one `instance.rollback` timeline (`available`, `toPrevious`, `toNext`, `subscribe`); do not create a second VN history stack.
- **Save safepoints**: add `saveGuard(publication)` to the web definition to disable manual saves mid-dialogue or mid-battle with a reason text.
- **Stage hit regions**: declare `hitRegions` in the content catalog and pass `onHitRegionActivate` to `SemanticStageV1`.
- **Motion assets**: narrative entrance/exit animations live in `src/motions/*.motion.json` (`sillymaker.motion` documents), bound through `motionStageTransition` in the transition catalog — never as inline duration/easing literals or CSS transitions in scene code (component-local hover effects stay CSS). `app check` lints every motion file (admission, unique ids, filename = id's final segment).
- **Content tables**: `defineContentTable` + `createContentDatabase` — static definitions go into tables (validated at resolve time), mutable state goes into modules.
- **UI styling**: only the published `--silly-*` tokens (no raw z-index; the stacking scales are in the style quick-reference of `docs/engine/authoring-quickstart.md`); gameplay windows declared with `defineWorkspaceOverlayV1` and resolved through `slots.overlayResolver` get the `PanelV1` chrome automatically; native form controls pick up the theme as-is.
- **Window model**: ordinary primary opens use the presentation-intent path; `context.overlays.openPrimary` is available for structural replacement, `pushDetail` stacks details, and `closeTop`/`closeAll` remove them. The Overlay facade is Coordinator-backed and its snapshot is read-only, so do not mirror it into another writable store or coordinate "open A, close B" yourself. Definitions requiring a port/service name it in `requiredPortIds` and the application supplies the concrete `overlayPorts` binding. An optional resolver `prepare()` may prepare presentation/resources only, never send semantic commands. System dialogs retain their existing single-slot lifecycle; separately, a Workspace Overlay definition may set `dismissible: false`. For dragging / minimize / maximize needs, follow the game-side recipes in `docs/engine/design/window-model.md` first (coordinates through viewport conversion, positions in Story UI state); promote to the engine only once the pattern recurs.

## Script/text tasks (most common)

Which file to edit: dialogue control and stable text references → the pure-data interaction document in `src/story/narrative.ts`; narrative copy → the build-known packs under `assets/content/` plus their compact manifest in `src/content/text-content.ts`; resident UI copy → `src/content/presentation.ts`. One short block name still derives node/interaction/text ids, and every derived id has an explicit override. `src/story/narrative-kit.ts` owns block admission and the Player control compiler; the dev-only read-only Flow projection lives separately in `src/tooling/narrative-flow.ts` and joins those stable IDs to authoring copy, but there is no longer a Flow workspace. Scene composition lives in `src/scenes/opening/opening.authoring-scene.json` (use the Inspector for its supported fields or edit the source directly); stage renderers live in `src/ui/stage-renderers.tsx`; product HUD/panel components live in `src/application/ui.tsx`; the public Narrative definition and default VN Player selection live in `src/application/composition.tsx`.

Adding one dialogue line = one control block plus one pack entry with the same textId. Keep early/late content in separate packs when `textContent.requiredPackIdsForInvocation` or `requiredPackIdsForSnapshot` can declare the later pack for Web's single Core readiness binding; do not add a parallel UI-local `ensure` or content facade. Scenario steps (`src/tooling/simulation-target.ts`) and playthrough tests resolve the _current_ pending interaction, so inserting lines does not renumber them; only steps that explicitly pin an `expectedOccurrenceId` (the stale-fence exercises) care about numbering.

Verification loop after every edit (seconds):

```sh
deno task typecheck
deno run -A npm:vitest run <this package directory>
deno task app simulate <appId> --scenario <name>
```

Rules in brief:

- Every new say/choice needs a brand-new short `name` (the kit derives `interaction.<story>.<name>` from it); never reuse one. Renaming a block changes its ids — saved histories reference textIds, so treat renames as intentional breaks (or pin the old id with the block's `textId` override).
- A `stage` block references scenes only through `ops` (`{ scene, cue }` per cue, `{ scene, open: true }` for a whole-scene open, plus script-owned `setAppearance`); the kit derives `mayShow` and the cue `dispatches` annotations from those references, and a `branch`'s arms must resolve inside the document (construction and the graph lint reject violations).
- New stage content is wired in three places: the contentId constant in narrative, the content catalog in presentation, and the renderer in `src/ui/stage-renderers.tsx`. `src/tooling/inspector-binding.ts` reuses that catalog and renderer registry for the dev-only preview; it has no second content manifest. Add the object and placement to the Authoring Scene source because the bounded Inspector does not yet create objects.
- Saveable state holds integers only (logical units like `scalePermille`); floats are rejected by canonical JSON.
- Scene cues use ensure semantics (`show` places or content-swaps idempotently; `hide` removes what is present); low-level `show`/`replace` mutations remain for non-scene-managed stages.

## Module/state tasks

**A new gameplay feature = a new slice directory**: put the feature's whole contribution under `src/game/features/<name>/` (`module.ts` module definition with its domain-event reducers, `content.ts` content tables, `rules.ts` pure rules, `handlers.ts` command handlers, UI components); aggregation points gain one line each (the handler map in `simulation.ts` and the table list in `content.ts`; a missed command kind fails to compile). Shared shapes (command/domain-event/verdict types, schema helpers, the kit) live in `src/game/kernel.ts`; this package's `game/features/inventory/` is the minimal sample. Scale by adding cohesive slices rather than growing aggregator files into feature owners.

Four wiring points: `game/state.ts` (interface + schema + initial value) → `game/features/<name>/module.ts` (module owner) and `game/features/<name>/handlers.ts` (commands) → `application/semantic.ts` (action catalog + blockedBy) → `game/simulation-definition.ts` (manifest entry; module ids in lexicographic order). Keep the package identity revision in `story.ts` synchronized. The revision-sync table and the diagnostics quick-reference are in `docs/engine/authoring-quickstart.md`; do not bump revisions from memory.

## Motion collaboration contract

Motion assets remain the human tuning surface. The current Inspector can resolve and scrub referenced Motion data without writing the draft; edit Motion JSON through ordinary source tooling until a future dedicated editor is accepted:

- Do not overwrite a motion file whose `authoring.status` is `"human_tuned"` or whose `authoring.locked` is `true` unless the task explicitly names that asset; to change a locked asset's feel, create a new variant file with a new motion id and rebind the transition.
- Preserve stable motion ids and transition ids when regenerating or restructuring scenes; a scene refactor may rebind which motion an edge uses, but must not regenerate existing motion files.
- New animation that a human may want to tune goes into a new `*.motion.json` (status `"generated"`), not inline constants.

## Scene collaboration contract

The opening is scene-managed: `src/scenes/opening/opening.authoring-scene.json` is the single authoring authority for its ordered Layer/Object hierarchy, local transforms, visual content/appearance, cue bindings, and presence-bound ambient references. Vite compiles that source into the runtime-only plan imported by `src/scenes/opening/index.ts`; do not duplicate placement/order declarations in gameplay code or mutate the same composition through a parallel low-level Scene path. Stage blocks reference stable scene/cue IDs through `ops`, while mid-scene `setAppearance` beats remain script-owned. Keep sceneId/objectId/cueId stable across refactors and let `app check` enforce admission, identity, and referenced Motion rules.

The dev-only `src/tooling/inspector-binding.ts`, declared as `inspector` in `sillymaker.config.ts`, supplies only the catalog and real Stage renderers that source discovery cannot infer. The Project Authoring Index discovers Authoring Scene and Motion documents; the binding and authoring implementation stay out of the Player graph. The old Scene Construction, Content, Motion, Regions, Chrome, and Flow workspace shell is gone. The underlying Narrative Flow projection, `sillymaker.regions`, `sillymaker.chrome-layout`, Motion, and runtime presentation contracts remain valid data/code surfaces; edit and validate them directly rather than recreating a second editor inside the Story.

## Forbidden

- Import only `@sillymaker/*` package exports; never import engine `src/**` paths, never import another Story.
- For engine-behavior questions read `docs/engine/features.md`; do not guess from engine source.
- Do not loosen assertion semantics to make tests pass; when occurrence assertions mismatch, renumber per the failure message.
