## Story authoring and resolution

- Typed `GamePackage`, `GameSimulation`, and `GameplayModule` definitions.
- A dedicated `@sillymaker/base/authoring` entry with `createRuntimeSchemaV1` (canonical-JSON output, deep-freeze, structured failures) and `fromStandardSchemaV1`, the official Zod adapter accepting any Standard Schema V1 implementation without leaking library types.
- `createGameAuthoringKitV1`: typed capability tokens, `requires`/`provides` with provider factories that build narrow read-only ports from the owner's State slice, a validated capability availability DAG plus an independent `initializesAfter` lifecycle DAG (stable diagnostic codes for missing/duplicate providers, cycles, and undeclared token access), stateful/stateless module helpers with derived proposal schemas, and composition into ordinary low-level module bindings. The low-level `defineGameplayModule`/`defineGameSimulation` API remains the escape hatch; one composition owns one resolved module graph.
- A composition-level transaction runner (`createTransactionRunner`) for cross-owner atomic commands: `read(token)` observes the command-start Snapshot, each owner accepts at most one proposal (duplicates fault with a stable diagnostic), proposals apply in canonical module-ID order so declaration order never changes the candidate, and the engine owns slice replacement, schema/invariant validation, fact collection, commit/reject/fault envelopes, and RNG/sequence rollback. `commitAttemptV1`/`rejectAttemptV1`/`faultAttemptV1` are also public for hand-written executors.
- A shared versioned `DiagnosticEnvelopeV1` (stable code, severity, phase, subject, JSON-pointer location, suggestion, Strict JSON details) used by authoring/definition/resolution failures, plus `collectGamePackageDiagnosticsV1` to aggregate a package's failures as structured diagnostics with human and JSON output.
- Separate simulation (`rule | value`) and presentation (`value | text | asset`) patch surfaces.
- Validated, frozen resolution with Story, engine, state-contract, simulation, presentation, asset, and patch-set identity.
- Story-local schemas, deterministic rule providers, command executors, queries, ViewModel projectors, scene graphs, catalogs, and renderer contributions.
- Optional lazily loaded Story tooling and tooling UI.

- The Base application composer (`@sillymaker/base/runtime`): `defineCoreGameApplicationV1` declares a Host-neutral core application (GamePackage entry, semantic adapter, validators, diagnostics extensions — no React, no Host handle); `resolveCoreGameApplicationV1` produces an immutable reusable resolved definition with structured failure reporting; `createCoreGameApplicationInstanceV1` creates a disposable instance that owns the Session, semantic port, persistence lease, diagnostics buffer, and lifecycle (`restart`). Failed construction and idempotent disposal leave no active owner or listener. Each instance maintains an instance-local presentation anchor/epoch that advances when the authoritative replay base is replaced (load/import/restart/debug anchor, with origin labels) and never enters SemanticPublication, semantic revisions, or Agent transcripts; `bindToCurrentEpoch` guards stale presentation callbacks structurally. Autosave is an injectable policy (`every_commit` default, or `debounced` with `delayMs`, optional `checkpointEveryCommands`, an injectable scheduler for deterministic tests, and `flushAutoSave` for pagehide-style hosts); explicit slot saves remain available under any policy. Low-level constructors (`createGameSessionV1`, `createPersistenceServiceV1`, `createSemanticGamePortV1`) stay public as escape hatches.
- `@sillymaker/base/testkit` ships `createGameHarnessV1`: a deterministic headless Game harness composed on the core application composer, so tests and real applications share one lifecycle contract. Stories supply only their semantic adapter (queries, projections, action catalog, previews, invocation mapping); the harness provides observe/preview/dispatch/waitForIdle, a deterministic trace, state digests, the persistence port, the underlying `application` instance, an admin surface (command log, authoritative replay, capability-gated debug control, explicit `inspectForTest`), and structured outcomes after disposal. The normal surface exposes no raw Snapshot or State setter.
- A Host-neutral `AgentGamePortV1` (`@sillymaker/base/runtime`): identity plus the player-safe SemanticGamePort operations with a bounded `waitForIdle` (timeout/AbortSignal return structured results without touching gameplay State). Save/import/export and read-only diagnostics are independent revocable capabilities (`createAgentPersistenceCapabilityV1`, `createAgentDiagnosticsCapabilityV1`); a revoked capability answers with `capability_revoked`. `createAgentTranscriptRecorderV1` records operation/result transcripts and `compareAgentTranscriptsV1` checks cross-host parity; the harness exposes `agent` plus capability grants for headless runs.
- `@sillymaker/tooling` (Node-only) hosts the versioned JSONL agent protocol: `createJsonlAgentHostV1` serves hello/observe/describeActions/preview/dispatch/waitForIdle over stdin/stdout-style streams (stdout carries protocol lines only; logs go to the injected sink), gates persistence/diagnostics methods behind explicitly granted capabilities, enforces line/depth/time limits with bounded structured errors and no stack leakage, and shuts down gracefully. `createJsonlAgentClientV1` is the matching minimal client. The method set is closed: no eval, no file paths, no DebugTools. Node in-process and JSONL runs of the same transcript produce identical semantic results and final digests.
- The UI composer (`@sillymaker/ui`): `GameViewportV1` maps a declared logical canvas (design resolution) onto the window with continuous fit scaling, themed letterbox/pillarbox, a `maxScale` center-stop, and read-only two-space conversion queries (`useGameViewportV1`) so renderers never build a second measurement authority. `createGameUiCompositionV1` composes the runtime presentation store (semantic projection plus the instance-local presentation anchor and Story UI state — never polluting SemanticPublication or Agent parity), input router, presentation intent router, and overlay/system dialog sessions with one disposal that revokes every subscription. `DefaultGameRootV1` is a complete playable shell with zero Story React code: viewport-managed seven-layer stage, designed default surfaces (Save overlay, Settings dialog, system menu), Story slots for stage/HUD/narrative/overlay contributions (adding one never modifies the composer), stage-space remount keyed by the presentation epoch, and a hard player/debug boundary — resident player DOM carries no debug vocabulary, machine probes are `data-*` only, and DevDock appears solely behind the `debug_tools` capability.
- The Web composer (`@sillymaker/web`): `startWebGameApplicationV1(application)` boots a complete browser application from one Story declaration (core definition + projector/catalog/slots/labels): web Host, the persisted capability session (Host records overlaid by the page request), core application instance (with Story extensions, live capabilities, and the application build digest), UI composition, default GameRoot mount, capability-gated browser automation bridge, optional pointer-adapter installation, lazy capability-gated DevDock contribution loading, DebugBundle UI-context binding, page-lifecycle teardown, and an idempotent `dispose` that unmounts, revokes listeners and automation generations, disposes Story UI resources, and releases the persistence lease. Story web entries contain no Session, Persistence, Diagnostics, Input, Automation, or HMR wiring: `installWebGameApplicationHmrV1` owns the dev accept boundary, fencing the predecessor, handing its persistence disposition to the successor (`rebootstrapDisposition`), and installing the next boundary. The Engine Lab boots through this one declaration path; Story diagnostics services, DebugBundle codecs, and debug tooling are Story extensions the composer constructs, and diagnostics export lives in the DevDock — the resident player DOM carries no debug vocabulary.
- The engine browser suite (`deno task test:e2e:engine`) validates the engine against the Engine Lab Story in real browsers: default shell boot and play, save round-trips across reloads, DOM/Browser-Agent publication parity with player-safe results, capability gating and the player/debug boundary, WCAG A/AA sweeps, GameViewport letterbox geometry across declared viewports (including a 16:10 tablet and 200% zoom), reduced-motion, and touch taps — each declared Playwright project executes real cases, and every test enforces a pageerror/console diagnostic policy.
- The Engine Conformance route is the vertical acceptance: one short real path through two backgrounds, two characters, and a prop with all three transition kinds (background crossfade, character-entry slide, appearance cut), BGM/ambient/SFX/voice intent, typewriter, a choice whose precise branch atomically consumes a sample cross-module (narrative + samples + stage owners in one committed command), and the return to the ordinary SLG surface. The route completes through DOM clicks, the Node Agent port, the JSONL host, and the browser automation bridge; normal, reduced-motion, skip, and Browser-Agent runs export byte-identical authoritative simulation states; headless same-seed runs produce identical digests and command logs with authoritative replay passing; and mid-route save/load converges on the same end state. The Lab ships no media bytes, so every green run also proves the missing-image/missing-audio degrade paths.
- The AI-authoring canaries prove the authoring surface with real extension tasks implemented entirely on the Story side (zero engine `src` edits, verified by the package's public-import-boundary guard over every `.ts`/`.tsx` source): a currency/shop module (`lab.wallet` owns its slot; selling a sample and buying the stage banner each commit one atomic cross-module command with stable rejection codes and untouched digests on refusal), a relationship-conditioned narrative branch (a Story-side `branch` node kind routes the beta line on `rapport`, which is authoritative narrative State that enters Saves; a conformance test replays every branch chooser against its static successor annotations, and prediction collects both conditional lines without deciding), and a semantic React shop overlay (renders exclusively from the published projection with catalog-provided blocked reasons and dispatches ordinary semantic invocations). Deterministic acceptance lives in ordinary test code across headless, jsdom, and browser suites; model evals remain non-blocking trend instruments.
- `@sillymaker/tooling/project` owns the Story/application project config: `defineSillymakerProjectV1` validates a plain-data application registry (story entry, asset verification, simulation target, optional web dev/build target) with structured diagnostics, and `runProjectCliV1` provides six lifecycle verbs over any declared application, each answering JSON: `inspect`, `check` (one or `--all`), `simulate` (with `--scenario` from the target's named scripts and `--seed` forwarded to the target factory), `dev --smoke` (boots the Vite dev server and proves the served page), `build` (the application's web target), and `prebuilt-smoke` (file-level Artifact verification). Simulation runs exclusively through the player-safe Agent port — both maintained applications declare targets built on the core composer — and process-level verbs run through an injectable runner so CLI contract tests cover the whole verb surface without spawning Vite. Repository consumers (Vite mode resolution, runtime asset verification, `deno task story`) all resolve applications through this one mechanism.

## Runtime

- `@sillymaker/base/story` is the Story authoring prelude: the current generation of every commonly authored contract re-exported under unversioned names (`SemanticStageState`, `StageMutation`, `PendingInteraction`, `NarrativeGraph`, `reduceStageMutations`, `evaluateInteractionResolution`, `defineCoreGameApplication`, …). It is a pure alias layer — a type-test matrix proves each alias identical to its versioned original — and it moves to a new generation together with the family it aliases. Versioned names remain the source of truth inside the engine; the superseded hand-assembly surfaces (`createGameRuntimeV1`, `createGameBootstrapControllerV1`/`Loader`, `createGameApplicationV1`, `useRuntimePresentationV1`) were removed once the composer path replaced their last consumer.

- One authoritative `GameSession` queue for gameplay dispatch and State replacement.
- Immutable, schema-validated `GameSnapshot` values; the session deep-freezes every installed Snapshot so live mutation attempts throw.
- Serializable purpose-labelled PRNG with rollback-safe command attempts.
- Structured commit, rejection, validation, and fault outcomes.
- Static module composition with explicit State ownership and dependency validation.
- Semantic preview/dispatch and immutable subscription publications for UI and automation.
- Lifecycle restart/rebootstrap and replay-base replacement.
- Semantic Stage contracts: versioned `SemanticStageStateV1` (ordered layers, stable `<layerId, tag>` entries, integer logical placement/appearance/camera targets) as plain canonical Save data, plus a pure atomic `reduceStageMutationsV1` batch reducer (`show`/`replace`/`hide`/`clearLayer`/`clearStage`/`setPlacement`/`setAppearance`/`setLayerTransform`/`setCamera`) that either commits a complete valid successor or rejects without touching the input state.
- Non-authoritative `StageRenderTargetV1` projection: a Story `StageContentCatalogV1` deterministically resolves semantic content into renderer IDs, asset IDs, accessible names, and Strict JSON props; unresolved content binds a code-native fallback renderer with structured diagnostics. The render target is rebuilt from State plus catalog and never enters a Save.
- Stage-driven projection wiring: Story game views may carry `SemanticStageStateV1` through the semantic publication (headless agents observe the semantic stage target), the Story UI projector rebuilds the render target every projection, and settled `requiredAssetIds` track the current target exactly — superseded assets leave the demand when the stage retargets.
- Stage transition contracts: plain, validated `StageTransitionDefinitionV1` data (cut/crossfade/slide, duration/easing, `block`/`target_active`/`skip_to_end` input policies, `settle_and_retarget`/`cancel_to_target` interruption, reduced-motion settle-or-fallback, immediate-or-bounded asset readiness, optional completion acknowledgment) plus a Story `StageTransitionCatalogV1` resolving old-to-new target changes. Definitions never enter the saveable stage state, and playing them never modifies gameplay State.
- `PendingInteractionV1`: the saveable interaction boundary (say, choice, pause, presentation barrier, and schema-registered custom surfaces) with three separated identities — author-stable `definitionId`, author-controlled `seenRevision`, and a per-entry-unique `occurrenceId` from a deterministic Story-owned sequence. `evaluateInteractionResolutionV1` is the single occurrence-fenced evaluator shared by the action catalog, preview, and queue-front dispatch; stale occurrences, wrong kinds, unknown or disabled choices, mismatched barrier transitions, and out-of-schema custom payloads reject without touching State. Renderer promises and callbacks never enter State or Saves.
- Typed audio media contracts: `AudioAssetSlotV1`/`AudioProviderEntryV1`/`resolveAudioManifestV1` keep music, ambient, SFX, and voice as their own contract (never images) with declared byte length and sha256 for response verification and a silence fallback. The saveable `AudioIntentV1` carries BGM/ambient channel targets (loop, permille gain, millisecond fades) and the current voice tied to its say interaction with a `stop_on_advance`/`sustain` policy; Saves reference stable asset IDs only.
- `AssetDemandPlanV1`: the explicit demand-plan contract (blocking/opportunistic priority, load group, concurrency budget, retry/backoff, retention) that loaders consume instead of accumulating one-shot requests; the budgeted plan scheduler integrates as media volumes grow.
- Typed Timeline contracts (R5): JSON-safe `TimelineDefinitionV1` (sequence/parallel/wait/tween/repeat/event over integer overlay channels — offsets, scale, opacity — targeting stage entries or the camera) with the `timelineV1` builder producing the identical contract as a hand-written literal. `parseTimelineDefinitionV1` rejects unknown kinds, invalid durations/easings, unbounded or over-deep repeats, and parallel branches writing the same channel; pure `evaluateTimelineAtV1`/`timelineDurationV1` make sampling deterministic and timer-free.

- Story meta progress: `PlayerProfileV1.meta` is a monotone `entryId -> value` map on the Host profile (the Seen registry generalized) with `markMeta` on the profile store; it survives every Game Save, restart, and rollback, and legacy profile records parse as empty. Stories own the key vocabulary (album unlocks, endings reached); the cat-cafe album overlay renders content-table entries against profile unlocks.
- Player rollback (R7): an opt-in `CoreRollbackPolicyV1` gives an application a bounded ring of committed Snapshots (default-pinned outcomes — RNG state travels inside every Snapshot, so a rolled-back retry reproduces the same result) with `classify` marking hard-barrier commands (settlements, irreversible beats) that clear every checkpoint behind them. `instance.rollback` exposes `available`/`toPrevious`/`subscribe`; a rollback replaces the authoritative Snapshot, advances the presentation epoch with origin `rollback` (stage, audio, and pending interactions re-project settled), reseeds on load/import/restart, and never touches Saves. Player history and rollback stay distinct from the CommandLog and Debug replay; the Seen registry lives in the Host profile and survives rollback by design. The Engine Lab and the Cat Cafe (contest entry and postgame confirmation as barriers, a HUD one-step-back control) are its two consumers.

- Commit-only transient effects: `CoreSemanticAdapterV1.projectTransientEffects` derives one-shot effect requests (for example SFX) from committed command facts, and the application instance emits them through `subscribeTransientEffects` stamped with a monotonic per-instance sequence and the presentation epoch at commit time. Effects never enter State, Saves, publications, or Agent transcripts, and load/bootstrap publications carry no history.
- `NarrativeHistoryV1`: the bounded player-readable backlog as Story/Narrative authoritative State — it enters Snapshots and Saves, restores to the exact occurrence, and is marked for M3 rollback to travel with the checkpoint Snapshot. It stays independent of the CommandLog (engine evidence), the Seen registry (Host profile), and Debug replay.
- Narrative graph lint and prediction: Stories project their typed TS narrative IR into the JSON-safe `NarrativeGraphV1` (no parser, no DSL — `createNarrativeGraphBuilderV1` and a hand-written literal produce the identical contract). `lintNarrativeGraphV1` reports duplicate nodes, missing entry/successors/call targets, unreachable nodes, pure loops with no interaction boundary, and duplicate interaction definitions as structured diagnostics with stable codes and source/pointer locations. `predictNarrativeDependenciesV1` walks every branch and call from the current cursor under an explicit node/depth/asset budget — it never executes a command, consumes RNG, or decides a hidden choice — and `narrativePredictionToDemandPlanV1` maps the collected text/asset/stage dependencies to an opportunistic prefetch `AssetDemandPlanV1`.
- Playback QoL consumers: the Engine Lab narrative player and the Cat Cafe dialogue panel both drive `createPlaybackControllerV1` + `createTextRevealV1` from profile preferences (text speed, auto wait, skip policy) with Seen marking from the authoritative history, and the Cat Cafe renders the `NarrativeHistoryV1` backlog as its in-game history panel with speed/wait sliders in Settings.
- `createPlayerProfileStoreV1`: the per-story player profile (Seen registry keyed by author-controlled `seenRevision`, plus text speed, auto wait, skip policy, and volume preferences) persisted in the Host `settings` record namespace — outside every Game Save, so loads never rewind reading progress, and corrupt records fall back to defaults.

## Content database

- Story-defined static data tables: `defineContentTableV1` validates a table at definition (table-id pattern, per-row RuntimeSchema parsing — typically zod via `fromStandardSchemaV1` — unique non-empty string primary keys, row limits); `createContentDatabaseV1` validates cross-table references at construction and exposes typed read-only views: `byId` (KV), `findMany`/`findFirst` with `where` conditions (eq/ne/in, numeric comparisons, array membership) and ordering, plus `collectTextIds` for text-catalog joins. Content is authoring-time data: no runtime mutation, JSON-safe, deterministic, and part of Story identity through the ordinary source-digest path. Mutable game state stays in module state (atomic commits, Saves, rollback) — the static/dynamic boundary is the design's first principle. First real consumer: the cat-cafe example (activities, petting reactions, contest moves, rivals, album entries).

## Gameplay primitives

- Event pool: `parseEventConditionV1` validates restricted serializable condition trees (number/flag/label leaves, all/any/not composition, depth and branch bounds); `drawFromEventPoolV1` filters eligible candidates and draws through one purpose-tagged transactional-RNG roll with JSON-safe explanation data (considered, eligible weights, roll, winner) and an eligibility-preserving debug force. First consumer: the cat-cafe weekly regulars (conditions in content-table rows, draws inside the business transaction, explanations in facts).

## Persistence and compatibility

- Desktop-channel persistence: `createHttpHostRecordStoreV1` implements the atomic record store over a trusted local HTTP endpoint; the repository ships a Deno save server (`scripts/desktop/save-server.mts`) that serves a built Player from a fixed port and owns a real save directory (atomic per-file replace, optimistic revisions, one serialized commit queue). `startWebGameApplicationV1` selects it automatically when the page runs with `?records=local` or when the desktop shell injects `__SILLYMAKER_RECORDS__`.
- One-step desktop packaging: `deno task story desktop <app>` stages a thin shell (`scripts/desktop/shell-main.ts`) that serves the built Player from the compiled binary's embedded `dist/`, injects the local-records signal, and owns the save directory under the platform user-data location; the project config's `desktop` target (name, identifier, optional icon) drives `deno desktop` compilation into a double-clickable app bundle with the icon installed.

- Quick Save, automatic Save, and manual Save slots through a Host persistence facade.
- Canonical Save envelope encoding/decoding and strict import validation.
- Story, state-contract, engine, simulation, and patch-lineage compatibility information.
- Validated managed adoption for compatible simulation changes.
- Atomic record revisions, session lease/fencing, and HMR persistence handoff.
- Browser persistence through IndexedDB; injectable record stores for tests and other Hosts.
- File import/export through Host ports.

## Diagnostics and developer capabilities

- The human tuning channel: Stories implement the debugCommand contract (validated, atomically committed, logged with source `debug`); authoritative replay routes debug entries through the debug executor with the live session's integrity stamp; committed debug commands raise the same commit-only transient effects as gameplay. The DevDock hosts cheat-authority panels built on `DebugCommandPanelV1` behind the `debug_tools` + `cheats` capabilities (reference implementation: the cat-cafe 调参 panel — set stats, fast-forward days, force encounters).
- `story simulate --trace <dot.paths>` samples the Agent publication after every step into per-step trajectories (the balance loop: edit a content table, re-simulate, compare); `story diff <a.json> <b.json>` reports structured path-level differences via `diffPlainDataV1`.

- Bounded command log and runtime-failure buffer.
- Privacy-aware DebugBundle export with current identity, replay evidence, and Story diagnostics.
- Best-effort inspection and authoritative replay support.
- Capability-gated debug tools and cheats.
- Story-specific fixture/tooling hooks where a maintained product workflow needs them.
- Browser automation bridge over semantic actions, with revocation when capability or ownership changes.
- HMR invalidation and full runtime rebootstrap based on resolved identity.

## UI and presentation

- React game shell with a central layered stage and runtime error recovery.
- HUD, narrative, workspace overlays, system dialogs, Save UI, and diagnostic export UI.
- `SemanticStageHostV1`: renders a projected Semantic Stage target with stable `layerId:tag` DOM identities, layer/camera/placement composition from integer logical units, Story-registered entry renderers, and a code-native fallback plus diagnostic for unregistered renderer IDs.
- Presentation runs and the Stage Reconciler: an injectable `PresentationClockV1` (animation-frame or deterministic manual), a reusable `PresentationRunV1` lifecycle (start/pause/resume/skip/settle/cancel/dispose with exactly-once outcome fencing; the future Timeline reuses it), and `createStageReconcilerV1`, which derives commit-only transition occurrences from committed target edges, renders previous + target + retained exiting entries, unions retained-exit asset demand, gates input by policy, suspends on page visibility, honors reduced motion live, drops stale edges across epoch changes (load/rollback), and emits exactly-once completion acknowledgments.
- `SemanticStageV1`: the animated stage component owning one reconciler per mount — feeds it committed publication targets, exposes `data-stage-settled`/input-gate lifecycle attributes for automation, and disposes every tick and listener on unmount, so browser tests observe lifecycle signals instead of sleeping.
- Timeline player and cue wiring: `createTimelinePlayerV1` executes timelines on the shared PresentationRun/Clock lifecycle (pause/resume/skip/cancel, playback-rate fast-forward, watermark-fenced exactly-once events, instant settle under reduced motion), and `SemanticStageV1` binds a Story timeline catalog to the composition cue registry — `presentation.play_cue` intents play decorative overlay cues (one active cue; a new cue cancels the previous) whose channels compose over the settled rendering and always clear on completion. Timelines never touch gameplay State or Saves.

- DevTools data plane (R6.1/6.2): `@sillymaker/ui/debug` ships generic read-only inspectors — `DebugValueInspectorV1` (live JSON over any observe/subscribe source, string-snapshot stable, size-bounded) and `DebugNarrativeGraphViewV1` (projected narrative graph with lint annotations and the pending interaction highlighted). The Engine Lab contributes four lazy DevDock panels (semantic stage, interaction + history, audio intent, narrative graph) behind the `debug_tools` capability; they read the exact publication surface players and agents consume and expose no setters.

- Audio presentation: the Host-neutral `AudioHostV1` surface with a deterministic `createFakeAudioHostV1` for tests, and `createAudioPresenterV1`, which reconciles the Story's continuous audio intent per committed publication (idempotent replace/loop/fade, voice tied to say occurrences with stop/sustain and replay), plays each commit-only SFX at most once per presentation epoch through an instance-local consumed watermark, restores continuous intent across epoch changes without replaying history, and suspends/resumes with page visibility. `GameAudioV1` packages this lifetime as one component (host + presenter per mount, publication/effect subscriptions, page-visibility suspend, voice-replay registration) and subscribes to the player profile so the Settings volume/mute sliders drive the host live; the Engine Lab (silence-fallback degrade proof) and the Cat Cafe (real MP3 set: scene-driven BGM, resident rain ambient, one-shot cues mapped from existing transient effects) are its two consumers.
- VN player systems: `createTextRevealV1` (clock-driven typewriter whose cursor is UI transient state, instant under reduced motion) and `createPlaybackControllerV1` — an explicit normal/auto/skip machine that dispatches through the exact same interaction-resolution contract as manual input, waits for full reveal plus the configured beat in auto, honors `skip_read`/`skip_all`, and stops at choices, pauses, barriers, custom surfaces, and unread lines. Playback mode and timers never persist and never touch authoritative State; hide-UI is pure presentation.
- Input routing, focusable code-native controls, settings, symbols, reduced-motion support, and content preferences.
- Keyboard and gamepad adapters: `installKeyboardAdapterV1` maps `KeyboardEvent.code` to semantic input actions through the Input Router's context priority (keys focused on editable or interactive elements never double as stage shortcuts, so accessible DOM controls keep native behavior), and `installGamepadAdapterV1` runs a minimal poll loop with rising-edge detection that stops on disconnect, teardown, or disposal. Pointer, touch, keyboard, gamepad, and Agents form the same semantic intents; physical input events never enter the CommandLog — only the gameplay semantic command a handler ultimately dispatches does. Player/presentation control actions (`playerInputActionIdsV1`: auto, skip, history, hide UI, voice replay) never masquerade as GameCommands, and the default GameRoot installs Story-configurable action maps for its lifetime while exposing the router through the slot context.
- Asset registry with requested-asset loading, fault diagnostics, and code-native fallback.
- Runtime art pipeline, end to end: a Story declares `assetSlots` + `assetPacks` in its presentation facet (validated into the resolved manifest with bytes/sha256/dimensions per provider); the manifest rides `createExtensions` to the UI, which builds `createAssetRegistryV1` over the injected image loader and resolves per-usage URLs inside Story renderers, falling back to code-native drawing per asset. The repository Vite config serves `<storyRoot>/assets/**` at its repository-relative runtimePath in dev and copies it into dist on build, so one runtimePath is true in dev, production Player, and the desktop shell. `deno task check:assets` verifies the real files against the declared digests. First real consumer: the cat-cafe 23-piece art pack.
- Title screen and settings baseline: an optional `BootSplashV1` front card (studio marks / AI-generation notices; auto-dismisses, any click skips) precedes `TitleScreenV1` (front door with New game / Continue / Load game / Settings, optional key art behind a darkening gradient), both rendering in the system layer until dismissed, and `DefaultSettingsSectionsV1` gives every application master volume/mute (persisted Host preferences), a fullscreen toggle, and a developer-tools switch that persists the `debug_tools` + `cheats` capabilities together — the DevDock and Story tuning panels open from Settings and stay out of the game UI by default.
- System menu discipline: the system layer hosts **one modal dialog at a time** (`SystemDialogSessionStoreV1` routes `settings` / `saves`; opening one replaces the other, Escape closes). The Save dialog lives in this layer — above the narrative panel, with the whole gameplay tree inert while open — and lists every slot (current/previous autosave, quick, manual) with saved-at timestamps. A successful load or import closes the dialog and enters gameplay (the anchored `load`/`import` epoch origin also dismisses the title screen, which is how Load game works from the front door). Stories may declare a save **safepoint** (`saveGuard` over the live publication): manual writes are disabled with the stated reason (for example mid-dialogue or mid-contest) while autosaves and loads stay available; authoritative snapshots are atomic either way, so the guard expresses game-design intent rather than data safety.
- Stage layer order is a published contract (`stageLayerIdsV1`): background, character, scene interaction, HUD, narrative, workspace overlay, system — modal workspace overlays (album, journal…) paint above dialogue text by construction. Paint order is token-driven end to end: the stage scale (`--silly-stage-z-*`) must match `stageLayerIdsV1` exactly and the within-layer surface scale (`--silly-surface-z-*`: base < raised < front-door < splash < dialog-backdrop < dialog < confirm-backdrop < confirm) must stay strictly increasing — both guarded by `stacking-tokens.test.ts`, and raw z-index numbers are forbidden in engine and Story code.
- Window chrome: `PanelV1` is the shared in-game window frame (visible title bar, optional header actions, close control, keyboard-focusable scrollable body) — the `OverlayHostV1` wraps every workspace overlay in it, so gameplay windows (album, shop, inventory…) get consistent chrome for free, with content-first initial focus (the close button never steals it). Styling comes exclusively from the published `--silly-*` theme tokens (colors, spacing, radii, target sizes, stacking).
- Immutable presentation projection that combines semantic output with local presentation state without becoming gameplay authority.

- Stage hit regions: `StageContentResolutionV1.hitRegions` lets the content catalog resolve activatable regions per contentId + appearance (regions can move as a character grows); projection validates and bounds them, and `SemanticStageHostV1` renders them as focusable transparent buttons only when the Story passes `onHitRegionActivate`, so pointer, touch, and keyboard reach the same semantic invocation path. Regions are presentation data and never carry gameplay authority; availability stays with semantic actions and module rules. The empty scene-interaction layer no longer mounts, so it cannot swallow stage pointer input.

## Web Host and application delivery

- Explicit Story-to-application composition and React mounting.
- Injectable autosave/checkpoint policy with a debounced browser default (`defaultWebAutosavePolicyV1`: quiet-period flush plus an every-N-commands checkpoint backstop), so committed Snapshots stay saveable at any time but long dialogues never write IndexedDB per line; the pagehide teardown flushes any pending capture before releasing the lease.
- `createWebAudioHostV1`: the browser Audio Host — verifies fetched bytes against the declared length and sha256 before decode (mismatches degrade to silence with an integrity diagnostic), caches decoded buffers while letting failed loads open a new cycle on later demand, unlocks the AudioContext on the first user gesture (queued continuous channels apply on unlock; locked one-shots are dropped with a diagnostic, never replayed), applies permille gains with linear fades, and suspends/resumes/closes with page lifecycle. Autoplay denial and missing or undecodable media never block gameplay.
- Browser entropy, clock, logging, navigation, files, image loading, and IndexedDB adapters.
- Hash routing and query-driven development capabilities.
- Loader recovery when a Hotfix cannot be admitted.
- Vite development and static Player builds.
- Local Artifact preparation with legal notices and a technical manifest.

## Current non-goals and planned design areas

The engine does not currently provide a backend/account service, networked multiplayer authority, runtime LLM, ECS, SQL query layer, or a general-purpose database client for UI. These are descriptions of the present implementation, not permanent bans.

The script-language decision is durable: Story, Module, Narrative, UI, and official Hotfix code use TypeScript/JavaScript. SillyMaker does not plan Ren'Py DSL/Save compatibility, a custom script interpreter, or an untrusted-code security sandbox. Direct Host-global access remains possible JavaScript but is outside the supported engine API.

The Semantic Stage family (contracts, reducer, projection, transitions, reconciler, components), PendingInteraction, audio intent/presentation, and the VN player systems above are implemented. A typed Timeline, advanced media/renderer adapters, authoring DevTools/editors, and Player rollback remain planned in the [engine roadmap](roadmap.md); the retired V1 scene-graph stage system (StageSceneGraph, hit maps, spatial interaction surfaces, character rigs) was deleted with the first PoC rather than ported.

State access and persistence may be redesigned. The current exploratory direction is recorded in [the typed StateStore proposal](proposals/typed-state-store.md). Any adopted design should replace or simplify existing machinery rather than create two competing authoritative states.

The Engine Lab Story is a conformance rig, not a product design. Its module split, thresholds, and script exist to exercise engine contracts; new games should not copy them as gameplay guidance.
