## Public Agent Session/Run

- `@sillymaker/agent/session` 是 focused transport/provider-neutral 公共入口。它公开一个 observable client、
  connector/connection ports、snapshot/diagnostic/results 和 stream events，不公开 root Agent barrel。
- connection 只实现语义级 `start`、`submit`、`cancel`、`close`；client 另外拥有
  `connect`、`reconnect`、subscriptions 与 awaited `dispose`。`start` 无产品参数，`submit` 只接收非空
  `sessionId` 与 text。
- stream 只有 `output_text_delta`、bounded Strict JSON `output_data`、`run_completed` 与
  `run_failed`。client 以 `(sessionId, runId)` 拥有 active-run currentness、连续正 sequence、旧连接/旧
  lifecycle fencing、terminal retirement 和 diagnostics；`cancel_requested` 只确认请求已被接收，直到远端
  terminal 前 tuple 仍由 client 保持 current。connection generation 是内部实现，不进入 snapshot。
- connector 的 unknown response/event 在公共 client 边界做一次 bounded canonical projection 与 exact
  admission。submit response 必须先 settle，connector 才能交付该 Run 的首个 event；真实 wire 若乱序，
  产品 connector 负责 bounded reorder。
- 公共入口不包含 raw request envelope、request ID、Worker/network/provider wire、真实 backend、Agent
  Host、`UiArtifact` admission/renderer、deterministic fake、conversation persistence、tool/permission、
  OpenUI/A2UI 或 external-effect authority。Engine Lab 的 private Host 仅把中立 `output_data` 解释为
  `UiArtifact`；该语义不属于 Session 合同。
- SillyOS 的并行产品实现提供了 promotion 压力，但 downstream connector 迁移尚未 handoff。当前公共合同
  因此不能被描述为已经接通 Pi/provider、Program bootstrap、附件、数据库或动态 UI 产品闭环。

## Internal composition kernel

- `@sillymaker/composition` 提供 typed service/registry token、plugin、profile、scope、稳定
  graph identity、direct-plan compiler 与可逆 lifecycle。每个 profile 直接拥有一个 staging
  record/composite disposer；公开 API、Story 和 hot path 均不接触动态 lifecycle Context。
- Graph preflight 在 setup 前拒绝 missing/duplicate provider、duplicate registry entry、同 ID
  的不同 token object 与 dependency cycle。setup 失败逆序回滚；cleanup failure 形成诊断且继续
  sibling cleanup。
- authoritative mount 成功即永久 sealed，拒绝后续 registration。State-backed legacy application 通过
  `activateStateApplicationV1` 保证先编译 State module direct plan，再激活 factory 并创建
  Session；State compile 失败时 factory 仍为 inactive。live profile candidate 完整 mount 后还必须
  由 consumer publisher 确认；确认期间旧 snapshot/provider 仍 current，拒绝会回滚 candidate。
  完整 mount 已安装的 live effects 会与 predecessor 共存，所以必须 staging-safe、可完整回滚且不得
  成为 publication 前的 exclusive writer；任意 publisher 的部分外部 mutation 仍由 consumer 自己
  保持或恢复。X1-X4 boot identity 不进入 Save `simulationDigest`。
- dev-only Inspector/Authoring Host 是一个真实 live composition consumer：standalone 与 embedded shell
  将 binding/scene IO/motion IO 编译为同一 direct plan，且不公开任意 live-effect 输入。publication
  保留一个 visible React root；R1 candidate 先在 inert/offscreen、document-connected staging root
  等待 layout-effect commit，connected layout failure 因而不触碰 visible predecessor，accepted
  candidate 才进入原 root 并保留兼容的 local state。同步 visible render-factory failure 可回到旧
  plan；不承诺任意 visible side effect 可逆。清理按 React consumer 在先、composition providers
  在后的顺序执行，失败转为诊断；该 Host 不持有 authoritative Session/State。connected staging
  不等于 user-visible paint 或精确 on-screen geometry，重型 geometry tool 仍需自己的浏览器
  readiness evidence。
- X1 曾以私有 Cordis core 包裹已经由 SillyMaker 拥有的 staging/disposal；retain/remove A/B 证明它
  没有承担独立 Fiber tree、injection、isolation 或 publication 语义后，最终实现改为 package-internal
  direct lifecycle。该历史 checkpoint 只裁决 profile wrapper，不等于后续 AR1 extension-runtime
  selection；公开 exports、State/Save/replay 和维护中 Player 的 JavaScript/CSS application chunks
  当时均未改变。
- AR1 的 workspace-only `./internal/extension-runtime` 是与 profile kernel 分开的 private Direct
  runtime：neutral factory 可 direct mount 或交给 activation controller；required domain/local
  binding 在 mount 前 admission，optional sibling failure/retry 隔离，nested child/reversible effect、
  provider loss/recovery、late-result fence、predecessor retention 与幂等 async cleanup 由同一
  conformance contract 覆盖。historical Direct/Cordis 17-case A/B 后只保留 Direct，Cordis
  adapter/vendor/dependency 已删除；domain、Story 和 public contracts 不出现 Cordis/Context。
- 外部 X6.2/X6.3 workload 把 concrete registries 限制在 Session 前的 cold environment，并让
  compiler/runner 只保留 typed script、一个 runtime node index、choice maps 与 direct gate/effect
  functions。Simulation/semantic hot consumers 不查询 registry 或 lifecycle Context；兼容名称仍是
  同一个 singleton runtime 的 exact aliases。外部源码和内容不属于引擎 feature 或 fixture。

## Story authoring and resolution

- Typed `GamePackage`, `GameSimulation`, and `GameplayModule` definitions.
- A dedicated `@sillymaker/base/authoring` entry with `createRuntimeSchemaV1` (canonical-JSON output and structured failures) and `fromStandardSchemaV1`, the official Zod adapter accepting any Standard Schema V1 implementation without leaking library types. Parsed values follow ordinary JavaScript runtime semantics.
- `createGameAuthoringKitV1`: typed capability tokens, `requires`/`provides` with provider factories that build narrow read-only ports from the module's own State slice, disjoint State-slot ownership (exact and parent/child overlap fail at cold composition), a validated capability availability DAG plus an independent `initializesAfter` lifecycle DAG, stateful/stateless module helpers, and composition into ordinary low-level module bindings. The low-level `defineGameplayModule`/`defineGameSimulation` API remains the escape hatch; one composition owns one resolved module graph.
- A composition-level transaction runner (`createTransactionRunner`) for cross-module atomic commands under the domain-event model (parallel-monitors lane M1, 2026-08-20; M2 direct hot plan, 2026-08-24): `read(token)` observes the command-start Snapshot, the handler performs every gameplay refusal via `reject(...)` before emitting, and `emit(event)` journals a decided outcome after validating it once against the Story `eventSchema` — `emit` itself never rejects. Cold composition maps event kinds directly to UTF-16 module-ID-ordered subscribers. After `complete()`, the engine folds events in emission order without scanning unrelated modules, carries one running proposal per touched owner, validates each owner once, and materializes all touched slots through one sparse aggregate-State copy. ## Gameplay primitives

## Persistence and compatibility

- Game-shell native-behavior reset (`@sillymaker/ui` `installNativeBehaviorResetV1`, installed by the web composer by default; a Story opts out with `input: { nativeBehavior: false }` or tunes it via the same key of the unified `input` declaration on the web UI definition): a "reset CSS" for browser input defaults — suppresses the context menu, text selection, touch callouts, image drag, and hover-cursor changes document-wide so a Player feels like a game shell. Only editable controls (`input`/`textarea`/`select`/contenteditable) keep native selection, menus, and the text cursor automatically (their menu is the copy/paste surface); buttons and other interactive controls are application-owned — the browser menu stays suppressed there and right-click routes through the Input Router (`data-secondary-action` on controls, stage `secondary` mapping). Any subtree opts back in with `data-native-menu` (browser menu) / `data-native-text` (selection + text cursor); links keep the pointer cursor. Inside an opted-in subtree the boundary stays control-aware: non-editable control faces (buttons, links, summaries, options) remain unselectable — a debug panel with `data-native-text` gets a copyable status summary while its button labels stay controls. Document-scoped on purpose because Story overlays portal to `document.body`; disposal removes every installed piece. The reset is a presentation floor, not a semantic owner: its Window-bubble listener runs after the document-level pointer adapter, exposes no raw context-menu callback, and yields when that adapter has claimed the event, and the stage CSS keeps its own selection/zoom/scroll-chaining suppression for the shell subtree.
- Desktop-channel persistence preview: `createHttpHostRecordStoreV1` is the browser-side adapter for the trusted local records endpoint. The Deno save server and packaged shell validate same-origin JSON requests, bounded bodies, namespaces, revisions, paths, and stored records; their current JSON-file backend provides optimistic revisions, a serialized in-process queue, and atomic **per-record** replacement. It does not yet prove crash-atomic multi-record commits, cross-process CAS, or a portable collision-free filename mapping for arbitrary record keys, so it remains a preview/reference backend pending the [desktop durability plan](plans/2026-07-30-desktop-persistence-durability.md). `startWebGameApplicationV1` selects the HTTP adapter when the page runs with `?records=local` or the shell injects `__SILLYMAKER_RECORDS__`.
- Usable Desktop packaging preview: `deno task build:desktop` (where the application declares it; `deno task app desktop <app>` from the root) stages a thin shell shipped inside `@sillymaker/tooling`, serves the built Player from embedded `dist/`, injects the local-records signal plus one per-launch capability, and owns a save directory under the platform user-data location. All shell traffic is admitted only for the exact runtime-selected loopback origin; private records/download requests also require the captured capability and reject cross-site or mismatched-Origin traffic. Launch-specific HTML is uncached and cannot be framed by another page. The download bridge has bounded concurrency and body deadlines, atomically publishes no-clobber files, and removes cancelled partials. The shell adopts Deno Desktop's startup window; native close synchronously fences gameplay ingress, starts a renderer-side autosave flush, and reads only that close request's JSON receipt. A verified receipt first cancels only non-authoritative downloads still receiving bodies, then allows HTTP admission to stop, active record commits to drain, and the process to exit; a missing or failed receipt keeps the window, server, and download ingress alive, with no heartbeat, watchdog, or timeout force-exit. The app config's desktop name, reverse-DNS identifier, and optional icon drive `deno desktop`; the default output is a host-platform preview, and explicit supported `--target <triple>` flags add cross-compiled packages per OS (macOS `.app`, Windows `.msi` installer, Linux `.AppImage`) with optional payload compression. Signing/notarization, per-platform launch smokes, and durable-store promotion are not yet live capabilities.

- Quick Save, automatic Save, and numbered manual Save slots (`manual.1`..`manual.N`) through a Host persistence facade; the manual slot count is Story-configurable (`manualSaveSlotCount` on the core application definition, engine default 8, range 0–99; zero disables numbered manual slots). (Pre-release clean break: records stored under the retired bare `manual` slot key are no longer enumerated.)

## Web Host and application delivery

- Explicit Story-to-game composition and a separate neutral GUI-only React
  mounting path; neither product entry requires application code to construct
  Host or renderer lifecycle machinery.
- Injectable autosave/checkpoint policy with a debounced browser default (`defaultWebAutosavePolicyV1`: quiet-period flush plus an every-N-commands checkpoint backstop), so committed Snapshots stay saveable at any time but long dialogues never write IndexedDB per line; the pagehide teardown flushes any pending capture before releasing the lease.
- Multi-instance lease coordination (`createWebInstanceLeaseCoordinatorV1`, composed automatically by the web start path): one unique lease owner per started tab/window/process, a declared `instancePolicy` applied against a live holder (`take_over` seizes at boot and reports `lost` when seized back; `read_only` never contends; `wait` runs read-only until the holder exits, then claims with CAS semantics so it never steals from a faster contender; `unrestricted` re-seizes on every loss — explicit last-writer-wins), a free lease always claimed regardless of policy, and an observable role port (`state.getCurrent`/`subscribe`, `refresh`, manual `takeOver`) handed to `application.ui()` and the started handle, together with `clearAllSaves` (Core wipe: drain pending Auto Save, then every slot) so a Story debug dock never loops `savePort.clear`. Role freshness combines a poll with a same-origin BroadcastChannel nudge on seizures; fencing tokens still reject every write from a seized instance, so no policy can corrupt a newer save.
- `createWebAudioHostV1`: the browser Audio Host — fetches and decodes the provider at its logical runtime path without comparing it to an author-maintained length/hash receipt, caches decoded buffers while letting failed loads open a new cycle on later demand, unlocks the AudioContext on the first user gesture (queued continuous channels apply on unlock; locked one-shots are dropped with a diagnostic, never replayed), applies permille gains with linear fades, and suspends/resumes/closes with page lifecycle. Autoplay denial and missing or undecodable media never block gameplay.
- Neutral Application Host capabilities for IndexedDB records, files, metadata
  clock, and logging; the Game Domain admits browser crypto entropy separately.
  Image loading and routing remain explicit Web composition concerns rather
  than universal Host capabilities.
- Hash routing and query-driven development capabilities.
- Loader recovery when a Hotfix cannot be admitted.
- Vite development and static Player builds.
- Optional copying of project legal files into an explicitly selected offline
  output directory; hosted Players may deploy `dist-web/` directly and expose
  applicable licenses through an in-product page, accompanying files, or a
  stable link. Packaging, signing, and integrity workflows belong to the actual
  target platform.

## Current non-goals and planned design areas

The engine does not currently provide a backend/account service, networked multiplayer authority, runtime LLM, ECS, SQL query layer, or a general-purpose database client for UI. These are descriptions of the present implementation, not permanent bans.

The Save migration product surface described above is implemented: supported
identities have checked-in canonical bytes, single-slot inspection and bounded
backup/recovery are player-accessible, and the maintained five-fixture corpus
runs through Story lifecycle and four-runtime parity gates. Opaque low-level
custom runtime controls and explicit legacy prepare-callback callers remain
outside the composite migration guarantee. PF5/M3 is complete; current/next work
is owned only by the [production-floor sequence](plans/2026-07-30-production-floor-sequence.md).

The script-language decision is durable: Story, Module, Narrative, UI, and official Hotfix code use TypeScript/JavaScript. SillyMaker does not plan Ren'Py DSL/Save compatibility, a custom script interpreter, or an untrusted-code security sandbox. Direct Host-global access remains possible JavaScript but is outside the supported engine API.

The Semantic Stage family (contracts, reducer, projection, transitions, reconciler, components), PendingInteraction, audio intent/presentation, the typed Timeline, the DevTools data plane (runtime inspector and Narrative graph), Player Back/Forward, the VN player systems, the capability-gated debug-command channel, and named-scenario `app simulate --trace` plus `app diff` tooling above are implemented. A generic arbitrary-snapshot preview, editable Timeline/Blueprint authoring, audio/transition inspection beyond Inspector's read-only facets/scrub, the bounded Presentation Scene Graph, and advanced media/renderer adapters beyond the delivered audio intent stack remain planned in the [engine roadmap](roadmap.md); the retired V1 scene-graph stage system (StageSceneGraph, hit maps, spatial interaction surfaces, character rigs) was deleted with the first PoC rather than ported.

State access and persistence may be redesigned. The current exploratory direction is recorded in [the typed StateStore proposal](proposals/typed-state-store.md). Any adopted design should replace or simplify existing machinery rather than create two competing authoritative states.

The Engine Lab Story is a conformance rig, not a product design. Its module split, thresholds, and script exist to exercise engine contracts; new games should not copy them as gameplay guidance.
