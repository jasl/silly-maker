# Parallel monitors proposal（跨 pending 权威监视器）

状态：**提案（未接受，无活跃车道）**。2026-08-20 所有者追加两个正交方
向并同日裁决六个开放问题（见裁决记录）；概念按工业术语正名：**领域事
件 / 事件日志**（原工作名 events / append-only 更新）与**持久化安全点
/ 在途段**（原工作名 transitioning）。词汇命名、切片与验收由未来的活
跃计划拥有；排序仍归
[production-floor sequence](../plans/2026-07-30-production-floor-sequence.md)。

本文是 [Authoritative hold clock](./authoritative-hold-clock.md) 的后继
缺口：hold 交付了「两句台词之间的权威计时持有」（含滴与换帧），但 hold
本身是 pending——**独占叙事边界**。还有一族行为是「计时过程与玩家输入
同时活着」：玩家在菜单里想、在台词里点，权威数值仍按节奏走。这不是
hold 能表达的轴。

## 目标模式

绝大多数逐帧脚本对玩家是阻塞演出（期间无输入），hold 已覆盖；本案只针
对真并行的三型：

1. **决策 gauge**：一条权威计量随时间上涨，玩家在**活菜单**里随时点
   击，点击时刻的档位决定分支结果。计时累积与 choice pending 同时活
   着——hold 装不下（hold 期间没有菜单）。
2. **场景窗自燃**：场景开关门控的在场滴——玩家逐句推进对白的同时，警
   戒/进度类计量每 N 帧自行调整。
3. **持续交互期滴**：持住某个交互面（长按、持有物件）时按节奏往权威计
   量累积。

共性：**一段权威数值随时间累积，寿命由权威状态门控（开关/字段），与当
前 pending 是谁无关**。

石蕊与 hold 案同款：这段时间有没有玩法意义。新增的一问是**「计时期间
玩家能不能动」**——不能动 → hold；能动 → 监视器。

## 调研（MV 与其他引擎怎么做）

| 引擎                      | 并行模型                                                                                                                                                                                       | 权威性 / 可回放                                                 |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| RPG Maker MV/MZ           | 单线程帧循环：`Game_Map.update` 先 tick 阻塞解释器，再按事件 ID 序 tick 每个 `trigger=2` Common Event 的独立 `Game_Interpreter`；共享 `$gameVariables/$gameSwitches`；开关门控，关掉即 refresh | 帧序固定 → 确定性；存档序列化解释器位置；无命令日志，回放靠重跑 |
| Ren'Py                    | 对话阻塞；并行只在表现层（ATL transform、screen `timer` action）。timer 可写变量但与 rollback 相性差，社区惯例避免                                                                             | 时间不进存档；mid-flight timer 不可序列化                       |
| Twine (SugarCube/Harlowe) | `<<timed>>/<<repeat>>`、`(live:)` DOM 宏                                                                                                                                                       | 同上：passage 边界外的计时不进存档                              |
| ink                       | `thread` 只交错叙事内容，无钟；时间完全在宿主                                                                                                                                                  | 权威在宿主，ink 侧确定                                          |
| Naninovel (Unity)         | 命令 `wait:false` 异步并行，主要用于表现                                                                                                                                                       | 状态快照制，异步命令完成态入档                                  |
| Godot / Unity             | 万物 `_process(delta)` / `Update`；Timer 节点、协程                                                                                                                                            | 浮点 delta，默认不确定；确定性要自己搭固定步长                  |

可取的组合：**MV 的确定性来自「单一帧钟 + 固定 tick 序 + 共享状态」**，
而不是来自解释器本身；VN 系引擎则一致把并行压到表现层、代价是这类玩法
（gauge 决策、在场滴）做不了或做了存不了档。SillyMaker 已有比 MV 更强
的底座：命令日志 + 阈值穿越算术（`countHoldTickCrossingsV1`，批切不变
性已单测锁定）。缺的只是**把经过时间喂给非 pending 的计时过程**的词汇。

## 正交性（与已有轴的分界）

| 轴                 | 拥有                                                 | 本提案不碰                                       |
| ------------------ | ---------------------------------------------------- | ------------------------------------------------ |
| `hold`（pending）  | 两句之间的独占计时演出：剩余、到期去向、滴、换帧     | 语义冻结；其时间入口按裁决 #1 归并进唯一时间动词 |
| 权威监视器（本案） | 与 pending 并行的计时累积：gauge、在场滴、场景窗自燃 | 不是第二套叙事 VM，不路由叙事                    |
| ambient / Timeline | 零权威装饰循环（呼吸、眨眼、制作名单擦除）           | 不滴权威、不进 Save                              |
| 输入轴             | 热区、命中区                                         | 与时间无关                                       |

## Shape（推荐形态草图；字段名以未来 admission 为准）

### 1. 声明：cadence + 领域事件，不是脚本

Story 侧注册监视器定义：

- `activeWhen`：权威状态谓词（复用 branch `when` 词汇）。MV 用开关门
  控，这里用领域字段门控——**没有 arm/disarm 动词**，效果写状态、谓词
  翻转即启停（对齐 MV 开关模型，也避免第二套生命周期 API）。
- `everyMs` + 事件载荷：阈值穿越结算（与 hold 滴同一算术），每次穿越
  发射声明的领域事件，reducer 在同一 commit 内应用（见方向 A；按裁决
  #4，监视器不再走「注册效果命令」仪式）。
- 累积保留策略：默认 `activeWhen` 翻 false 清零（对齐 MV 开关关掉
  refresh）；按裁决 #2，`retain`（暂离保留、回来续涨）作为声明字段随
  V1 一起实现。
- 可选 `frames` / 投影通道：gauge 档位换帧、HUD 条读累积毫秒。
- **不做脚本体**。监视器是「节奏 + 事件」的声明，不是可编程解释器；需
  要顺序演出的用 hold，需要复杂逻辑的写进 reducer。

### 2. 状态：会话内可序列化累积

`{ [monitorId]: accumulatedMs }` 是权威会话状态的普通版本化数据：Save
中途保得住 gauge；清零/保留按声明策略执行。回放吃命令日志，不重读墙
钟。

### 3. 喂钟：唯一时间动词（裁决 #1、#3）

硬规则：**同一段墙钟流逝只允许进权威一次**。裁决后的形态——

- 归并为**唯一时间动词**（工作名 `time_tick({elapsedMs})`，最终命名随
  实现车道定）：会话级报时，一次 commit 内结算全部时间消费。
  `hold_tick` 并入后删除，沿 pause→hold 归并删除的先例做一次显式重构
  迁移（admission、Host 提议、facade、测试与文档一并换名，不留双动
  词）。
- 同一 commit 内结算顺序固定：先折当前 hold pending 的余量（若有），
  再按注册序推进所有活跃监视器（阈值穿越，批切不变）。总消费毫秒 =
  报告毫秒，不存在双计窗口。
- 流逝源：**Host 表现钟是唯一流逝源**（限定 JS/浏览器环境，时钟可靠性
  足够——所有者裁决）。权威只消费报告的毫秒数；墙钟时间戳仍不进
  State、Save、digest。表现冻结端口停止提议即全局停表。
- say/choice pending 期间由 Host 按 `tickQuantumMs` 同款纪律分批报
  时；输入 resolution 本身不携带时间。MV 的「全时」（每帧 tick 一切并
  行事件）不照搬进合同——报时节奏与停表策略归 Host/应用层。
- 顺序确定性：监视器推进序 = 注册序（MV 事件 ID 序的等价物）；时间报
  告与输入 resolution 的交错由命令日志如实记录，回放同序。

### 3a. 倍速与跳过（fast-forward / skip；推荐形态，未裁决）

VN 惯例的加速（按住 Ctrl 二倍速）不是 Host 时间源的副作用，而是本合同
刻意留出的自由度，拆成两个既有概念：

- **倍速 = 时间缩放（timeScale）**：Host 报时前给真实流逝乘播放速率
  （Unity `Time.timeScale` / HTML 媒体 `playbackRate` 同款）。真实 1s
  报 2,000ms，命令日志记录的就是 2,000ms——回放逐毫秒一致，digest 与
  速率无关；批切不变性保证「同样总毫秒，快报慢报终态相同」。滴与换帧
  照常发生，只是真实世界里更快。速率与偏好存 Host profile（settings
  namespace，同 auto/skip 偏好），不进 State、Save、digest。
- **跳过 = 折叠（fold）**：skippable hold 的余量一次折清（既有
  `narrative.resume` 词汇）；skip 模式即自动折叠连续的 skippable
  hold，不需要新机制。
- **公平性提示**：唯一的真问题是交互计时窗——决策 gauge 在 2x 下玩家
  反应窗减半，这是游戏设计问题而非确定性问题。沿 `skippable` 先例给
  hold/监视器加声明式节奏提示（工作名 `pace: cinematic | realtime`）：
  cinematic 可缩放可折叠；realtime 窗 Host 不应用倍速、skip 至此停
  （Ren'Py skip 在菜单前停下的同款惯例）。提示只约束 Host 行为，不进
  权威算术。

### 4. 与 HUD / 表现

投影读会话观察面的累积毫秒（与 hold 条读 pending 剩余同款），不开第二
口钟。gauge 档位换帧走 `frames` 同族阈值，不写进 flipbook。

### 5. 明确不做

- 复活 MV 并行解释器 / 第二套叙事 VM / 监视器脚本体。
- `Date.now()` / rAF 进 State、Save、digest。
- 逐帧命令成为推荐用法（quantum 分批纪律沿用）。
- 把 ambient 装饰循环或热区输入迁到监视器上。
- 监视器路由叙事（改写 pending / 跳段）。中止改道仍是 hold `when` 的
  defer 词汇，等第一条真实路径。

## 追加方向 A：领域事件与事件日志（2026-08-20 所有者）

所有者提议：在稳定权威钟的基础上引入 append-only 的事件更新模式——组
件只要发射事件即可完成更新，事件由谓词产生还是代码产生不重要。正名为
工业术语：**领域事件（domain event）** 为更新单元，**事件日志（event
journal）** 为落盘序列。

**分析。** 引擎的既有形态已经是「append-only 输入 + 确定性折叠」：命
令日志就是输入流。所以问题不是「要不要 append-only」，而是**哪一层获
得 append-only 的人体工学**。两种形态要分开：

- **事件作为第二条外部输入流**：不推荐。它只是命令改名，还引入双流排
  序与双份 admission。外部输入（玩家、Host、自动化）继续走命令。
- **commit 内的领域事件**：值得。今天每个内部更新都要走「注册效果命
  令」的仪式；改成 **Story 声明的事件类型 + reducer 应用**后：
  - 生产者（监视器阈值穿越 = 谓词产生；效果代码 = 代码产生）在同一
    commit 内 emit 领域事件，携带权威毫秒时间戳；所有者判断成立——产
    地确实不重要，重要的是**都经唯一序列化写者**（transaction runner
    仍是唯一 appender），确定性由「谓词/代码只读已提交状态 + 权威钟」
    保证。
  - reducer 应用在同一 commit 内原子完成：权威状态更新 =
    `apply(state, events)`，失败即整体不动，原子纪律不变。
  - commit 落盘的事件序列即**事件日志**（读侧）：HUD、成就、统计、时
    间线调试面订阅增量，不再各自 diff 快照。这与 SemanticPublication
    互补——publication 是「当前面」，事件日志是「变化流」。
  - 回放合同不变：命令日志仍是唯一回放输入，事件日志可确定重导出；
    **不进 digest**、默认不进 Save（诊断可留有界环形缓冲）。

**范围（裁决 #4：全量一步到位）**：注册效果命令家族整体迁移到「领域事
件 + reducer」，不做双轨过渡——按研发期纪律破坏式重塑，显式迁移并删除
旧权威路径；监视器 V1 直接以事件为唯一产出通道。**风险与停**：事件一
旦可以绕过序列化写者、或消费者从事件日志重建出第二份权威状态，就退化
成双权威——停。

## 追加方向 B：持久化安全点与在途段（2026-08-20 所有者）

所有者提议：为有副作用的阻塞动作增加不可持久化的过渡状态，让状态导出
更安全。正名为工业术语：**持久化安全点（persistence safepoint）** 为
可导出的稳定状态，**在途段（in-flight span）** 为副作用未收束的多
commit 括号，编排器在途期执行**存档抑制（autosave inhibit）**。对齐的
工业实践：JVM/GC 只在 safepoint 暂停检查、存储/虚拟化先静默
（quiesce）再快照、systemd 以 inhibitor lock 在关键操作期抑制挂起。

**分析。** 单 commit 原子已有；真实缺口在**多 commit 逻辑动作**（装配
→演出→收束的 span、外部副作用括号：音频解锁、平台调用、桌面持久化
IO）。span 中间的已提交状态合法，但不宜作为再入点——现在导出/自动存
档看不出这一点。

推荐形态：

- 安全点判定：优先从既有 pending kind 推导（`presentation_barrier` 天
  然在途），再给显式在途段声明（commit 内进入/退出，入院强制有界）。
- 存档抑制：持久化编排器在途期把 autosave **推迟或落回最近安全点快
  照**；导出永远只见安全点状态。span 内的 scratch 状态**不序列化**——
  这把原子性从单 commit 扩展到声明的 span：崩溃恢复回滚到 span 前安全
  点，正是想要的语义。
- 分界必须写死：监视器累积、hold 剩余毫秒是**长寿权威状态，必须入
  档**，不属于在途段；在途段只括短的、有副作用的多 commit 过渡。
- 风险与停：span 无界会饿死存档（入院强制有界）；在途段不得成为藏非确
  定性或第二个非版本化状态店的地方（后者是
  [typed-state-store](./typed-state-store.md) 的领地）。

**落地（裁决 #5）**：设计以本提案固化；实现拟随 Desktop persistence
durability 车道一起领——该车道本就拥有持久化编排与崩溃语义，安全点/
存档抑制是其自然词汇。

与本案的关系：监视器不依赖安全点，但两者共享「导出安全」叙事——gauge
中途导出靠可序列化累积（§2），副作用过渡导出靠安全点回落。

## 裁决记录（2026-08-20，所有者）

1. **动词归并**：归并为唯一时间动词，接受为此所需的显式重构
   （`hold_tick` 并入后删除，沿 pause→hold 归并删除先例；不留双动
   词）。
2. **累积保留**：`retain` 策略随 V1 引擎侧一起实现（清零/保留按监视器
   声明字段选择）。
3. **时间源**：Host 表现钟为唯一流逝源——限定 JS/浏览器环境，时钟可
   靠性足够；权威只消费报告毫秒。MV 式「全时」（每帧 tick 一切并行事
   件）不写进合同，报时节奏与停表策略归 Host/应用层。
4. **事件范围**：全量一步到位——注册效果命令家族整体迁移到「领域事件
   - reducer」，显式迁移并删除旧路径，不做双轨。
5. **安全点**：设计先行（本提案固化形态），实现拟随 Desktop
   persistence durability 车道一起领。
6. **监视器首消费者**：三型一步到位——决策 gauge、场景窗自燃、持续交
   互期滴各一条活路径在同一车道交付，不做逐型分期。

剩余开放（随实现车道定，不阻塞接受）：唯一时间动词与事件家族的最终命
名、admission 字段名、事件日志的诊断缓冲上界、`pace` 提示的字段形态
（§3a，倍速/跳过策略）。

## 验收草案（随接受锁定）

- Headless：同一监视器在 `{500,500,500}` 与 `{1500}` 批切下终态
  digest 相同；时间报告与输入 resolution 交错重放同序同终态。
- 归并动词：hold pending 期间唯一时间动词在同一 commit 内先折余量再推
  监视器，总消费毫秒 = 报告毫秒（无双计）；迁移后全仓无 `hold_tick`
  残留。
- Save：gauge 中途存档，load 后累积保留，续报到档位分支同一出口；
  `retain` 与清零两种策略各有单测。
- 事件：同一命令日志两次回放重导出的事件序列逐条相同；清空事件缓冲不
  影响权威终态与 digest；旧注册效果命令路径删除后全部消费者走事件日
  志。
- 安全点（随 Desktop 车道）：在途段内触发 autosave 落回最近安全点快照
  并可正常 load；span 退出后恢复正常粒度。
- 三型消费者各一条活路径端到端：gauge 档位点击、场景窗在场滴启停、交
  互期滴累积——门控翻转启停、HUD 读同一累积、玩家中途点击拿到正确档
  位。

## 停

沿用 production-floor §9 与 hold 案的停条件；本提案特有：

- 监视器获得脚本体或路由权（改 pending / 跳段）；
- 同一段墙钟流逝进权威两次（双钟并行报时）；
- 为监视器发明第二套生命周期 API 而不是状态谓词门控；
- 领域事件成为第二条外部输入流，或消费者从事件日志重建第二份权威；
- 在途段被用来藏非确定性、或长寿权威状态借它逃出 Save；
- 归并动词重构中途停在双动词并存状态。
