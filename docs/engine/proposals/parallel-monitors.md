# Parallel monitors proposal（跨 pending 权威监视器）

状态：**提案（未接受，无活跃车道）**。本文只固化问题形状、调研与推荐
形态；词汇命名、切片与验收由未来的活跃计划拥有。排序仍归
[production-floor sequence](../plans/2026-07-30-production-floor-sequence.md)。

本文是 [Authoritative hold clock](./authoritative-hold-clock.md) 的后继
缺口：hold 交付了「两句台词之间的权威计时持有」（含滴与换帧），但 hold
本身是 pending——**独占叙事边界**。原作还有一族行为是「计时过程与玩家
输入同时活着」：玩家在菜单里想、在台词里点，权威数值仍按帧走。这不是
hold 能表达的轴。

## 证据门

外部实验仓（`tmp/imouto-native`）已把厕/素股/澡三族计时窗全部按 hold
落地（刀 #297/#298/#299）。落地过程反复验证了同一条判据：**MV 的
`trigger=2` 大多不是真并行**——CE293/CE300 装配后内联 CALL（阻塞演出）、
CE275/274 虽真并行但主流程 `LOOP{WAIT 1f; IF V156==0}` 自旋 join，对玩家
可观察行为都是无输入定时演出，hold 合同即可 100% 落地。

筛完之后剩下的才是本提案的靶子（实验仓 `docs/fidelity-gaps.md` 记
ENGINE 的三条）：

- **澡 CE274 V156=3 口交 gauge**：共浴フェラ期间 CE274 并行画一条随
  时间上涨的 gauge，玩家**随时**可在活菜单里点「射精」，点下那一刻的
  gauge 档决定结果分支。计时累积与 choice pending 同时活着——hold 装
  不下（hold 期间没有菜单）。
- **CE277 見せつけ/共浴进行度自燃**：SW15 场景窗内每 50f 调警戒
  V155、V157≥4 再减——玩家逐句点台词的同时表在走。现克隆只画投影
  条、不滴（已接受的暂时欠保真，fidelity-gaps E2 表「留后」行）。
- **CE281/282 深夜持 cut-in 逐格滴**：持住抚摸 cut-in 时每 60f×8 往
  快感/嫌悪 +=。现克隆把触摸折成一次命令 / 3 tick——终态对、过程节奏
  不对。

共性：**一段权威数值随时间累积，寿命由权威状态门控（SW/V 开关），与
当前 pending 是谁无关**。原作还有第四族（CE243 时刻 HUD 的 +10 分轮
询、CE242 状态表示）已按「效果净额直接拨钟」适应收敛，不再要求并行。

## 调研（MV 与其他引擎怎么做）

| 引擎                      | 并行模型                                                                                                                                                                                       | 权威性 / 可回放                                                 |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| RPG Maker MV/MZ           | 单线程帧循环：`Game_Map.update` 先 tick 阻塞解释器，再按事件 ID 序 tick 每个 `trigger=2` Common Event 的独立 `Game_Interpreter`；共享 `$gameVariables/$gameSwitches`；开关门控，关掉即 refresh | 帧序固定 → 确定性；存档序列化解释器位置；无命令日志，回放靠重跑 |
| Ren'Py                    | 对话阻塞；并行只在表现层（ATL transform、screen `timer` action）。timer 可写变量但与 rollback 相性差，社区惯例避免                                                                             | 时间不进存档；mid-flight timer 不可序列化                       |
| Twine (SugarCube/Harlowe) | `<<timed>>/<<repeat>>`、`(live:)` DOM 宏                                                                                                                                                       | 同上：passage 边界外的计时不进存档                              |
| ink                       | `thread` 只交错叙事内容，无钟；时间完全在宿主                                                                                                                                                  | 权威在宿主，ink 侧确定                                          |
| Naninovel (Unity)         | 命令 `wait:false` 异步并行，主要用于表现                                                                                                                                                       | 状态快照制，异步命令完成态入档                                  |
| Godot / Unity             | 万物 `_process(delta)` / `Update`；Timer 节点、协程                                                                                                                                            | 浮点 delta，默认不确定；确定性要自己搭固定步长                  |

可取的组合：**MV 的确定性来自「单一帧钟 + 固定 tick 序 + 共享状态」**，
而不是来自解释器本身；VN 系引擎则一致把并行压到表现层、代价是这类玩法
（gauge 决策、在场滴）做不了或做了存不了档。SillyMaker 已有比 MV 更强
的底座：命令日志 + 阈值穿越算术（`countHoldTickCrossingsV1`，批切不变
性已单测锁定）。缺的只是**把经过时间喂给非 pending 的计时过程**的词汇。

## 正交性（与已有轴的分界）

| 轴                         | 拥有                                                 | 本提案不碰                    |
| -------------------------- | ---------------------------------------------------- | ----------------------------- |
| `hold`（pending）          | 两句之间的独占计时演出：剩余、到期去向、滴、换帧     | 语义不变，合同冻结照旧        |
| 权威监视器（本案）         | 与 pending 并行的计时累积：gauge、在场滴、场景窗自燃 | 不是第二套叙事 VM，不路由叙事 |
| ambient / Timeline（P0-2） | 零权威装饰循环（呼吸、眨眼、制作名单擦除）           | 不滴权威、不进 Save           |
| E3 输入轴                  | 热区、命中区                                         | 与时间无关                    |

石蕊与 hold 案同款：**这段时间有没有玩法意义**。新增的一问是**「计时
期间玩家能不能动」**——不能动 → hold；能动 → 监视器。

## Shape（推荐形态草图；字段名以未来 admission 为准）

### 1. 声明：cadence + 效果，不是脚本

Story 侧注册监视器定义（与 effect registry 同族）：

- `activeWhen`：权威状态谓词（复用 branch `when` 词汇）。原作用
  SW15/V156 门控，克隆用领域字段门控——**没有 arm/disarm 动词**，
  效果写状态、谓词翻转即启停（对齐 MV 开关模型，也避免第二套生命周期
  API）。
- `everyMs` + 注册效果命令：与 hold `tick` 同一结算法（阈值穿越）。
- 可选 `frames` / 投影通道：gauge 档位换帧、HUD 条读累积毫秒。
- **不做脚本体**。监视器是「节奏 + 效果」的声明，不是可编程解释器；
  需要顺序演出的用 hold，需要复杂逻辑的写进效果命令。

### 2. 状态：会话内可序列化累积

`{ [monitorId]: accumulatedMs }` 是权威会话状态的普通版本化数据：
Save 中途保得住 gauge；`activeWhen` 翻 false 即清零（对齐 MV 开关关
掉 refresh 解释器）。回放吃命令日志，不重读墙钟。

### 3. 喂钟：单一时间报告，一次 commit 消费一次

硬规则：**同一段墙钟流逝只允许进权威一次**。推荐形态——

- 经过时间报告是会话级动词（暂名 `time_tick({elapsedMs})`），一次
  commit 内按注册序推进所有活跃监视器（阈值穿越，批切不变）。
- 当前 pending 是 hold 时，既有 `hold_tick` 的 `elapsedMs` **在同一
  commit 里同时喂监视器**——不存在两条钟并行报时的窗口。
- say/choice pending 期间，Host 按 `tickQuantumMs` 同款纪律分批报
  `time_tick`；输入 resolution 本身不携带时间。表现冻结端口停止提议
  即全局停表，语义与 hold 一致。
- 顺序确定性：监视器推进序 = 注册序（MV 事件 ID 序的等价物）；时间
  报告与输入 resolution 的交错由命令日志如实记录，回放同序。

### 4. 与 HUD / 表现

投影读会话观察面的累积毫秒（与窗条读 pending 剩余同款），不开第二口
钟。gauge 档位换帧走 `frames` 同族阈值，不写进 flipbook。

### 5. 明确不做

- 复活 MV 并行解释器 / 第二套叙事 VM / 监视器脚本体。
- `Date.now()` / rAF 进 State、Save、digest。
- 逐帧命令成为推荐用法（quantum 分批纪律沿用）。
- 把 ambient 装饰循环或 E3 热区迁到监视器上。
- 监视器路由叙事（改写 pending / 跳段）。中止改道仍是 hold `when` 的
  defer 词汇，等第一条真实路径。

## Open questions（留给所有者）

1. **动词归并**：`time_tick` 与 `hold_tick` 是「一个时间轴两个入口」。
   是否照 pause→hold 的先例最终归并成单一时间动词（hold 场景下同时
   结算 pending 剩余）？hold 合同刚交付且冻结，本文只标注方向，不在
   提案里重开。
2. **累积保留**：`activeWhen` 翻 false 清零是推荐；是否需要 `retain`
   变体（场景暂离再回继续涨）等第一条真实路径再领。
3. **时间在哪些 pending 期间流动**：MV 全时流动；推荐 V1 由 Host 报时
   节奏决定（应用侧策略），不在合同里枚举 pending 种类。
4. **首消费者**：推荐澡 V156=3 口交 gauge（词汇覆盖最全：门控 + 累积
   - 档位分支 + 与活菜单并行）；CE277/CE281 滴随后各一条证明复用。

## 验收草案（随接受锁定）

- Headless：同一监视器在 `{500,500,500}` 与 `{1500}` 批切下终态
  digest 相同；时间报告与输入 resolution 交错重放同序同终态。
- Save：gauge 中途存档，load 后累积保留，续报到档位分支同一出口。
- 双钟互斥：hold pending 期间的时间报告同 commit 喂监视器，总消费毫
  秒 = 报告毫秒（无双计）。
- 首消费者一条活路径端到端：门控翻转启停、HUD 读同一累积、玩家中途
  点击拿到正确档位。

## 停

沿用 production-floor §9 与 hold 案的停条件；本提案特有：

- 监视器获得脚本体或路由权（改 pending / 跳段）；
- 同一段墙钟流逝进权威两次（双钟并行报时）；
- 为监视器发明第二套生命周期 API 而不是状态谓词门控；
- 在没有真实消费者的情况下先做通用框架。
