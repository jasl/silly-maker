# Parallel monitors proposal（跨 pending 权威监视器）

状态：**提案（未接受，无活跃车道）**。2026-08-20 所有者追加两个正交方
向（append-only 事件更新模式、不可持久化 transitioning 状态），本文一
并固化分析。词汇命名、切片与验收由未来的活跃计划拥有；排序仍归
[production-floor sequence](../plans/2026-07-30-production-floor-sequence.md)。

本文是 [Authoritative hold clock](./authoritative-hold-clock.md) 的后继
缺口：hold 交付了「两句台词之间的权威计时持有」（含滴与换帧），但 hold
本身是 pending——**独占叙事边界**。还有一族行为是「计时过程与玩家输入
同时活着」：玩家在菜单里想、在台词里点，权威数值仍按节奏走。这不是
hold 能表达的轴。

## 目标模式

绝大多数逐帧脚本对玩家是阻塞演出（期间无输入），hold 已覆盖；本案只针
对真并行的三型：

1. **决策 gauge**：一条权威计量随时间上涨，玩家在**活菜单**里随时点
   击，点击时刻的档位决定分支结果。计时累积与 choice pending 同时活
   着——hold 装不下（hold 期间没有菜单）。
2. **场景窗自燃**：场景开关门控的在场滴——玩家逐句推进对白的同时，警
   戒/进度类计量每 N 帧自行调整。
3. **持续交互期滴**：持住某个交互面（长按、持有物件）时按节奏往权威计
   量累积。

共性：**一段权威数值随时间累积，寿命由权威状态门控（开关/字段），与当
前 pending 是谁无关**。

石蕊与 hold 案同款：这段时间有没有玩法意义。新增的一问是**「计时期间
玩家能不能动」**——不能动 → hold；能动 → 监视器。

## 调研（MV 与其他引擎怎么做）

| 引擎                      | 并行模型                                                                                                                                                                                       | 权威性 / 可回放                                                 |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| RPG Maker MV/MZ           | 单线程帧循环：`Game_Map.update` 先 tick 阻塞解释器，再按事件 ID 序 tick 每个 `trigger=2` Common Event 的独立 `Game_Interpreter`；共享 `$gameVariables/$gameSwitches`；开关门控，关掉即 refresh | 帧序固定 → 确定性；存档序列化解释器位置；无命令日志，回放靠重跑 |
| Ren'Py                    | 对话阻塞；并行只在表现层（ATL transform、screen `timer` action）。timer 可写变量但与 rollback 相性差，社区惯例避免                                                                             | 时间不进存档；mid-flight timer 不可序列化                       |
| Twine (SugarCube/Harlowe) | `<<timed>>/<<repeat>>`、`(live:)` DOM 宏                                                                                                                                                       | 同上：passage 边界外的计时不进存档                              |
| ink                       | `thread` 只交错叙事内容，无钟；时间完全在宿主                                                                                                                                                  | 权威在宿主，ink 侧确定                                          |
| Naninovel (Unity)         | 命令 `wait:false` 异步并行，主要用于表现                                                                                                                                                       | 状态快照制，异步命令完成态入档                                  |
| Godot / Unity             | 万物 `_process(delta)` / `Update`；Timer 节点、协程                                                                                                                                            | 浮点 delta，默认不确定；确定性要自己搭固定步长                  |

可取的组合：**MV 的确定性来自「单一帧钟 + 固定 tick 序 + 共享状态」**，
而不是来自解释器本身；VN 系引擎则一致把并行压到表现层、代价是这类玩法
（gauge 决策、在场滴）做不了或做了存不了档。SillyMaker 已有比 MV 更强
的底座：命令日志 + 阈值穿越算术（`countHoldTickCrossingsV1`，批切不变
性已单测锁定）。缺的只是**把经过时间喂给非 pending 的计时过程**的词汇。

## 正交性（与已有轴的分界）

| 轴                 | 拥有                                                 | 本提案不碰                    |
| ------------------ | ---------------------------------------------------- | ----------------------------- |
| `hold`（pending）  | 两句之间的独占计时演出：剩余、到期去向、滴、换帧     | 语义不变，合同冻结照旧        |
| 权威监视器（本案） | 与 pending 并行的计时累积：gauge、在场滴、场景窗自燃 | 不是第二套叙事 VM，不路由叙事 |
| ambient / Timeline | 零权威装饰循环（呼吸、眨眼、制作名单擦除）           | 不滴权威、不进 Save           |
| 输入轴             | 热区、命中区                                         | 与时间无关                    |

## Shape（推荐形态草图；字段名以未来 admission 为准）

### 1. 声明：cadence + 效果，不是脚本

Story 侧注册监视器定义（与 effect registry 同族）：

- `activeWhen`：权威状态谓词（复用 branch `when` 词汇）。MV 用开关门
  控，这里用领域字段门控——**没有 arm/disarm 动词**，效果写状态、谓词
  翻转即启停（对齐 MV 开关模型，也避免第二套生命周期 API）。
- `everyMs` + 更新载荷：与 hold `tick` 同一结算法（阈值穿越）。
- 可选 `frames` / 投影通道：gauge 档位换帧、HUD 条读累积毫秒。
- **不做脚本体**。监视器是「节奏 + 更新」的声明，不是可编程解释器；需
  要顺序演出的用 hold，需要复杂逻辑的写进注册的更新代码。

### 2. 状态：会话内可序列化累积

`{ [monitorId]: accumulatedMs }` 是权威会话状态的普通版本化数据：Save
中途保得住 gauge；`activeWhen` 翻 false 即清零（对齐 MV 开关关掉
refresh 解释器）。回放吃命令日志，不重读墙钟。

### 3. 喂钟：单一时间报告，一次 commit 消费一次

硬规则：**同一段墙钟流逝只允许进权威一次**。推荐形态——

- 经过时间报告是会话级动词（暂名 `time_tick({elapsedMs})`），一次
  commit 内按注册序推进所有活跃监视器（阈值穿越，批切不变）。
- 当前 pending 是 hold 时，既有 `hold_tick` 的 `elapsedMs` **在同一
  commit 里同时喂监视器**——不存在两条钟并行报时的窗口。
- say/choice pending 期间，Host 按 `tickQuantumMs` 同款纪律分批报
  `time_tick`；输入 resolution 本身不携带时间。表现冻结端口停止提议即
  全局停表，语义与 hold 一致。
- 顺序确定性：监视器推进序 = 注册序（MV 事件 ID 序的等价物）；时间报
  告与输入 resolution 的交错由命令日志如实记录，回放同序。

### 4. 与 HUD / 表现

投影读会话观察面的累积毫秒（与 hold 条读 pending 剩余同款），不开第二
口钟。gauge 档位换帧走 `frames` 同族阈值，不写进 flipbook。

### 5. 明确不做

- 复活 MV 并行解释器 / 第二套叙事 VM / 监视器脚本体。
- `Date.now()` / rAF 进 State、Save、digest。
- 逐帧命令成为推荐用法（quantum 分批纪律沿用）。
- 把 ambient 装饰循环或热区输入迁到监视器上。
- 监视器路由叙事（改写 pending / 跳段）。中止改道仍是 hold `when` 的
  defer 词汇，等第一条真实路径。

## 追加方向 A：append-only 事件更新模式（2026-08-20 所有者）

所有者提议：在稳定权威钟的基础上，把「事件」引入为另一种更新模式——
组件只要发送 event 做 append-only 式更新；event 由谓词产生还是代码产生
不重要。

**分析。** 引擎今天已经是一台事件溯源机：命令日志就是 append-only 输
入流，状态是确定性折叠。所以问题不是「要不要 append-only」，而是**哪
一层获得 append-only 的人体工学**。两种解读要分开：

- **事件作为第二条输入流**（与命令并列的外部入口）：不推荐。它只是命
  令改名，还引入双流排序与双份 admission。外部输入（玩家、Host、自动
  化）继续走命令。
- **事件作为 commit 内的内部事实**：值得。今天每个内部更新都要走「注
  册效果命令」的仪式（监视器 Shape §1 也沿用了它）；改成**Story 声明
  的事实类型 + 纯 reducer 折叠**后：
  - 生产者（监视器阈值穿越 = 谓词产生；效果代码 = 代码产生）在同一
    commit 内 append 事实，携带权威毫秒时间戳；所有者判断成立——产地
    确实不重要，重要的是**都经同一序列化写者**（transaction runner 仍
    是唯一 appender），确定性由「谓词/代码只读已提交状态 + 权威钟」保
    证。
  - 折叠在同一 commit 内原子完成：权威状态更新 = `fold(state, events)`
    ，失败即整体不动，原子纪律不变。
  - commit 落盘的事实序列同时成为**读侧日志**：HUD、成就、统计、时间
    线调试面订阅增量，不再各自 diff 快照。这与 SemanticPublication 互
    补——publication 是「当前面」，事件日志是「变化流」。
  - 回放合同不变：命令日志仍是唯一回放输入，事件可确定重导出；事件流
    **不进 digest**、默认不进 Save（诊断可留有界环形缓冲）。

**收益点名**：监视器落地即第一个生产者（阈值穿越天然是事实）；hold 到
期、效果结算、日结算等现有更新点可渐进迁移。**风险与停**：事件流一旦
可以绕过序列化写者、或消费者从事件流重建出第二份权威状态，就退化成双
权威——停。

## 追加方向 B：不可持久化的 transitioning 状态（2026-08-20 所有者）

所有者提议：为有副作用的阻塞动作增加不可持久化的「transitioning」状
态，让状态导出更安全。

**分析。** 单 commit 原子已有；真实缺口在**多 commit 逻辑动作**（装配
→演出→收束的 span、外部副作用括号：音频解锁、平台调用、桌面持久化
IO）。span 中间的已提交状态合法，但不宜作为再入点——现在导出/自动存
档看不出这一点。

推荐形态：**稳定点词汇化**。

- 会话级 `transitioning` 标记：优先从既有 pending kind 推导
  （`presentation_barrier` 天然是过渡态），再给显式 span 声明（commit
  内进入/退出，必须有界）。
- 持久化编排器咨询标记：过渡中 autosave **推迟或落回最近稳定快照**；
  导出永远只见 settled 状态。span 内的 scratch 状态**不序列化**——这
  把原子性从单 commit 扩展到声明的 span：崩溃恢复回滚到 span 前稳定
  点，正是想要的语义。
- 分界必须写死：监视器累积、hold 剩余毫秒是**长寿权威状态，必须入
  档**，不属于 transitioning；transitioning 只括短的、有副作用的多
  commit 过渡。
- 风险与停：span 无界会饿死存档（入院强制有界）；transitioning 不得成
  为藏非确定性或第二个非版本化状态店的地方（后者是
  [typed-state-store](./typed-state-store.md) 的领地）。

与本案的关系：监视器不依赖 transitioning，但两者共享「导出安全」叙
事——gauge 中途导出靠可序列化累积（§2），副作用过渡导出靠稳定点回落。

## Open questions（留给所有者）

1. **动词归并**：`time_tick` 与 `hold_tick` 是「一个时间轴两个入口」。
   是否照 pause→hold 的先例最终归并成单一时间动词（hold 场景下同时结
   算 pending 剩余）？hold 合同刚交付且冻结，本文只标注方向，不在提案
   里重开。
2. **累积保留**：`activeWhen` 翻 false 清零是推荐；是否需要 `retain`
   变体（场景暂离再回继续涨）等第一条真实路径再领。
3. **时间在哪些 pending 期间流动**：MV 全时流动；推荐 V1 由 Host 报时
   节奏决定（应用侧策略），不在合同里枚举 pending 种类。
4. **事件的落地范围**：只做监视器产出（最小），还是同步把注册效果命令
   家族迁到「事实 + reducer」（方向 A 全量）？推荐先最小、迁移渐进。
5. **transitioning 的第一消费者**：桌面持久化 IO 括号、还是演出收束
   span？推荐随 Desktop durability 车道一起领。
6. **首消费者（监视器）**：推荐决策 gauge 型（词汇覆盖最全：门控 + 累
   积 + 档位分支 + 与活菜单并行）；场景窗自燃与交互期滴随后各一条证明
   复用。

## 验收草案（随接受锁定）

- Headless：同一监视器在 `{500,500,500}` 与 `{1500}` 批切下终态
  digest 相同；时间报告与输入 resolution 交错重放同序同终态。
- Save：gauge 中途存档，load 后累积保留，续报到档位分支同一出口。
- 双钟互斥：hold pending 期间的时间报告同 commit 喂监视器，总消费毫秒
  = 报告毫秒（无双计）。
- 事件（若领）：同一命令日志两次回放重导出的事件序列逐条相同；事件流
  缺失（清空缓冲）不影响权威终态与 digest。
- transitioning（若领）：span 中触发 autosave 落回最近稳定快照并可正常
  load；span 退出后恢复正常粒度。
- 首消费者一条活路径端到端：门控翻转启停、HUD 读同一累积、玩家中途点
  击拿到正确档位。

## 停

沿用 production-floor §9 与 hold 案的停条件；本提案特有：

- 监视器获得脚本体或路由权（改 pending / 跳段）；
- 同一段墙钟流逝进权威两次（双钟并行报时）；
- 为监视器发明第二套生命周期 API 而不是状态谓词门控；
- 事件成为第二条外部输入流，或消费者从事件流重建第二份权威；
- transitioning 被用来藏非确定性、或长寿权威状态借它逃出 Save；
- 在没有真实消费者的情况下先做通用框架。
