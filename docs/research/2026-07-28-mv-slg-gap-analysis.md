# 研究笔记：中型 SLG（RPG Maker MV 重制）的引擎能力缺口分析

日期：2026-07-28。输入：一个外部 MV 参考（登记见 reference-register，版权状态不明，**本笔记只记录结构事实与量级，不含任何内容摘录**）。分析目标：一个市场验证过的中型养成 SLG 需要哪些引擎能力，SillyMaker 缺什么。

## 1. 目标游戏的技术画像（结构事实）

RPG Maker MV 标准布局，但开发方式证实了"RPG Maker 不适合 SLG"：

- **自带数据库被整体绕开**：Actors/Items/Skills/Enemies/Armors/Weapons/States/Troops/Classes 全部只有占位条目。原因显而易见——这些表的 schema 是 JRPG 专用的，养成 SLG 的数据装不进去。
- **一切活在事件系统里**：615 个公共事件共 9.7MB JSON，按命名前缀人肉分组（状态栏、立绘、战斗、白天/夜间命令菜单、各训练活动）。回合制战斗也是事件脚本手搓的（呼叫→战力→指令→敌方行动→结束判定），未用引擎战斗系统。
- **状态 = 1621 个全局变量 + 303 个全局开关**：按数组索引寻址、无类型、无命名空间、无校验。约 30 个核心数值（时间/星期/金钱/行动力/精力/多维好感与状态值/公会评价），其余是活动进度、立绘控制、触摸命中标记等杂项混堆。
- **UI 全部重造**：54 个第三方插件（消息、选择列表、仪表、图片按钮、触摸、虚拟按键、存档界面、性能修补）。
- **触摸玩法**：图片区域点击插件 + 开关池标记命中部位，事件轮询开关做反应——空间交互是这个品类的核心玩法而非装饰。
- **图鉴/回忆**：图鉴类插件 + 事件解锁，属于跨周目元进度。
- **i18n 现状**：文本直接烧在事件指令里；汉化=逐事件改写。没有可维护的本地化通道。

## 2. 映射到 SillyMaker：已覆盖 / 缺口

| 该游戏的系统        | SillyMaker 现状                         | 结论                                |
| ------------------- | --------------------------------------- | ----------------------------------- |
| 对话/选择/分支      | PendingInteraction + 叙事脚本 + 图 lint | ✅ 更强（可静态验证）               |
| 立绘/舞台/表情      | 语义舞台 + 转场 + Timeline cue          | ✅ 更强（可存档、确定性）           |
| 日程与数值结算      | 模块模式可实现（wallet/samples 已验证） | ⚠️ 可写但样板多，见缺口 A           |
| 回合制战斗          | Story 模块可实现                        | ✅ 架构够用，缺一个 example 证明    |
| 存档/读档/回滚      | 持久化 + R7 rollback                    | ✅ 更强（该游戏靠引擎默认存档）     |
| 触摸/空间交互       | **无**（V1 hit map 随 PoC 删除）        | ❌ 缺口 C：品类核心玩法             |
| 图鉴/回忆（元进度） | Host profile 有 Seen registry 先例      | ⚠️ 缺口 E：需通用化命名空间         |
| i18n                | 文本目录有 locale 结构，内容单语        | ⚠️ 缺口 F：缺工作流不缺架构         |
| **大规模内容数据**  | TS 字面量（文本目录/内容目录）          | ⚠️ 缺口 B：千行级数据表的定义与查询 |

## 3. 缺口详述与优先级建议

**缺口 A+B——内容数据库（最高优先，两者同根）**。该游戏用 1621 个无类型变量 + 硬编码在事件里的数值规则，是"没有内容数据层"的下场：不可校验、不可查询、不可本地化、LLM 不可维护。RPG Maker 明明有数据库仍被绕开，说明**固定 schema 的数据库不够，需要自定义表**。SillyMaker 的对应设计见 [content-database 提案](../engine/proposals/content-database.md)：静态类型化内容表 + Prisma 风格查询 + KV 直取，运行时只读，进 Story 身份。可变数值仍归模块状态（该游戏把两者混在变量池里正是灾难根源）。

**缺口 C——语义舞台的可命中区域（品类硬需求）**。触摸互动是养成 SLG 的核心玩法。旧 V1 hit map 已随场景图删除；正确的重生形态是挂在语义舞台条目上的**命中区域声明**（stage content catalog 解析出的 hit regions + 语义交互意图），保持"物理输入→语义 action"纪律。这条作为 R5–R7 计划 defer 表之外的新真实需求证据记录；建议在第一个触摸玩法复刻实验前实现。

**缺口 E——元进度命名空间（低成本）**。把 Host profile 的 Seen registry 一般化为 Story 可声明的图鉴/成就命名空间（跨存档、不进 Game Save、可导出）。

**缺口 F——i18n 工作流（可后置）**。架构已支持多 locale 目录；缺的是缺失键检测、导出/导入与 locale 切换 UI。等第一个双语实验再做。

**非缺口——战斗**。用一个 examples 复刻实验证明模块模式写回合制战斗即可，不进引擎。

## 4. 对复刻实验计划的输入

该游戏本身**不可作为复刻任务书素材**（版权状态不明，见登记表禁止用途）。但它给出了品类形状：一个"日程 + 数值 + 触摸 + 图鉴"的原创设计规格可以覆盖缺口 A/B/C/E 的全部验证需求，建议作为内容数据库与命中区域落地后的第一个大型复刻实验。
